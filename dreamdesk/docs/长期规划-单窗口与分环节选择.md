# 长期规划：一个会话窗口、画面链路分环节选择

> 2026-10-27 与用户讨论后整理。**状态：只是长期方向，没有排期**——用户当天定「保持现状」，等将来换掉 Flutter（换成 Qt，见第 8 节）时一起做。
> Moonlight / Sunshine 的结论都对着源码核实过（`D:\WORKPLACE\CODING\_reference\`，moonlight-qt ac29686、moonlight-common-c 5d3c0ec、Sunshine 8aac196）。

## 1. 一句话

用户只看到**一个会话窗口、一套菜单**；画面链路的每个环节**各自**挑当时能用的最好做法——设备好就画质高，网络通就延迟低，
哪一项不够只退那一项，不再「缺一条就整个换成另一种模式」。

## 2. 先分清两件事：适配设备、适配网络

讨论里最容易混的地方。两件事互不相干，分开判断：

| | 适配设备 | 适配网络 |
|---|---|---|
| 解决什么 | 主控端 / 被控端的硬件能做什么 | 两台机器之间连不连得通、走哪条路 |
| 管哪几个环节 | 采集、编码、格式 / 颜色、解码、上屏 | 画面走哪条线、码率、丢包补救 |
| 决定的是 | **画质**（4:4:4 还是 4:2:0、HDR、硬解还是软解） | **延迟和能不能连上** |

三家对比：

| | 适配设备 | 适配网络 |
|---|---|---|
| RustDesk | 能（编码格式、软硬解按两头能力选） | 能：直连、打洞、中继，哪里都连得上；画面和键鼠、文件挤在同一条连接里 |
| Moonlight / Sunshine | 能（格式、解码、上屏都有退档） | 只能直连（内网、端口映射或 VPN）；画面单独一条线 |
| 我们（目标） | 能 | 能：内网时画面走画面专线（学 Moonlight），拉不起来就和别的东西一起走主连接（保留 RustDesk 的本事） |

## 3. 术语：主连接、画面专线

打个比方：**主连接**像一通电话，先经总机（ID 服务器）接通，接通方式按网络情况是直接通、打洞通或经中继转接，什么事都在这通电话里说；
**画面专线**是我们另拉的一根线，不经总机、直接连到被控端的内网地址，只传画面，只有在内网够得着时才拉得起来。
「画面走主连接」就是不拉专线、画面和别的东西挤在那通电话里传——RustDesk 原本一直这样。
「直连 / 打洞 / 中继」只用来说主连接是怎么接通的，不再拿「直连」给画面专线起名（10-27 改，原来叫「会话连接 / 画面直连」容易混）。

| | 主连接 | 画面专线 |
|---|---|---|
| 是什么 | RustDesk 原有的连接，每次远程都有 | 我们额外开的一条，只传画面 |
| 怎么建立 | 经 ID 服务器牵线 | 主控端直接连被控端的内网地址，不经服务器 |
| 走哪条路 | 直连、打洞或中继，按网络情况 | 只能内网直连 |
| 协议 | TCP 或 UDP（打洞后用 KCP，`src/kcp_stream.rs`）；中继是 TCP | UDP |
| 装什么 | 键鼠、剪贴板、文件、控制消息，以及通用模式的画面 | 只装画面 |
| 加密 | 有 | 有（密钥经主连接交换） |

**为什么画面要单独一条线**：主连接是「可靠连接」，丢一个包后面所有数据都要等它重传（队头阻塞），画面就顿一下；
画面专线由我们自己处理丢包——要么补发、要么放弃这帧要关键帧，不拖住别的数据；30 Mbps 的画面也不和文件、剪贴板抢道。
这是从 Moonlight 学的（它的画面也单独走一个 UDP 端口）。RustDesk 没有单独的画面线：主连接即便走 UDP，也是一条什么都往里塞的可靠连接。

**专线管的是延迟和流畅，不管画质**：

- 画质由编码那一侧决定（4:4:4 还是 4:2:0、HDR、码率、静止画面补成无损），和画面走哪条线无关。画面走主连接，编码照样可以选 4:4:4 硬编、主控端照样硬解。
- 专线解决三件事：延迟低（不和别的数据排队）、丢包时不卡顿（没有队头阻塞）、不和文件 / 剪贴板抢带宽。
- 所以外网只要画质、不苛求延迟时，画面走主连接就可以，可靠传输还保证不会因丢包花屏，代价是网络差时偶尔顿一下。
  真正的限制是带宽（尤其走中继）：码率给不到 30 Mbps 时，动的画面清晰度差一些，静下来照样能补到清晰甚至无损。
- 现在一离开专线就整体退回通用画面，连 4:4:4 也一起丢了——这正是「整体打包」的损失，分环节选择后就不会了。

**专线的建立方式**：

| 方式 | 现在 | 能不能做 | 建议 |
|---|---|---|---|
| 内网直连（主控端直接发 UDP 到被控端内网地址） | 有 | — | 保持 |
| 打洞（借 ID 服务器交换公网地址、两边同时互发 UDP） | 没有 | 能，中等工作量：外网带宽小要能调码率，往返延迟高要加前向纠错（P1 对照 WebRTC 的规则：延迟高时用纠错、不靠补发），对称型 NAT 照样打不通 | 以后在外面用的人多了再做，排在第 8 节主计划之后 |
| 中继 | 没有 | 现有中继服务器只转 TCP，走它就又有队头阻塞，和直接走主连接没区别；要做得另部署 UDP 中继（类似 TURN），画面流量全压在服务器上 | 不做：外网打不通时画面走主连接即可 |

以前说的「UDP 专业通道」把**一条连接**和**一种画质组合**（显卡直编、4:4:4、HDR、直接上屏）捆在一起叫，以后不再用：
画面走哪条只是一个环节的选择；「专业」只是**各环节都选到最好档时的结果**，界面上可以继续叫「专业画质」。

## 4. 现在的做法：两条整体打包的路线

| 环节 | 通用模式 | 专业模式 |
|---|---|---|
| 被控端采集 / 编码 | RustDesk 视频服务（VP9 / H.264 / H.265 等） | 我们的显卡直采直编（HEVC 4:4:4，HDR 时 10bit） |
| 画面走哪条 | 主连接 | 画面专线；丢包靠重传补发 |
| 主控端解码 / 显示 | Flutter 远程窗口（解出来当贴图画） | Linux 原生专业窗口（硬解后直接上屏） |
| 菜单 | 标题栏控制中心（Flutter） | 悬浮球（专业窗口自己画） |

专业模式要**下面每一条都满足**才进得去，缺任何一条整个退回通用模式：主控端是 Linux Wayland、显卡能硬解 HEVC 4:4:4、
画面专线连得通（被控端内网地址可达）、被控端是 Windows 且能直采硬编。

**问题**：

- 缺一条就全盘退回，连带丢掉本来能用的好东西。例：主控端能硬解 HEVC 但不支持 4:4:4，现在被打回通用画面（可能还是软解），
  合理的是照样用画面专线和硬解、只把颜色降成 4:2:0；又如走中继时被控端明明能显卡直编，现在也只能用 RustDesk 的编码。
- 设备和网络两件事被捆成一个开关：网络不通（在外面）也会连带丢掉设备上的优势，反之亦然。
- 两个会话窗口、两套菜单、两套功能，来回切换；Flutter 窗口装不下专业画面（不能把一块区域交给显卡直接上屏、不支持 HDR），只能另开窗口。
- 当初这么做是务实的第一步：整体打包能不碰 RustDesk 原有视频路径（薄钩子规则），最快做出专业画质。

## 5. Moonlight / Sunshine 是怎么做的（已核实）

- **网络上只有一条路**：一组视频参数、一个视频端口；没有中继、没有打洞、没有备用线路（STUN 只用来查本机公网 IP），外网靠端口映射或 VPN。
- **连接开始时协商一次，由主控端决定**：被控端只报告自己支持哪些编码档；主控端按自己能不能硬解给候选排序
  （AV1 / HEVC / H.264，各分 10bit 4:4:4 → 10bit → 8bit 4:4:4 → 8bit），取第一项；被控端只校验。
- **设备这边各环节各有后端和退路**：被控端采集（Windows 桌面复制 → WGC；Linux 六种）、编码器（NVIDIA → Intel → AMD → 软件，开机探测、全机一个）、
  主控端解码（三档硬解 → 软解）、上屏（各平台一个渲染器，统一接口）。
- **串流中途不调整**：编码格式不换、码率固定、没有自适应；4:4:4 不会自动降成 4:2:0（被控端编码器不支持就直接失败）。
- **丢包**：前向纠错（Reed-Solomon）→ 参考帧作废 → 请求关键帧。
- **窗口**：串流时另开一个 SDL 原生窗口、Qt 主界面藏起；统计面板由渲染器直接画在画面上；串流窗口里没有菜单，只有快捷键。
- **许可**：三个项目都是 GPLv3（Sunshine 写明只限 v3），可以和 RustDesk 的 AGPLv3 一起用。

## 6. 目标：各环节分别选

**一条链路，每个环节各有选项；「传输」这个环节的选项恰好是两条线路**：

```
采集/编码 → 格式/颜色 → [传输：画面专线 或 主连接] → 解码 → 上屏
 （设备）     （设备）          （网络）           （设备） （设备）
```

- **设备适配**是链路上的几个环节各自挑档，互不牵连，哪个不够只退哪个。
- **网络适配**只管「画面走哪条」这一个环节：画面专线、主连接二选一；码率和丢包补救跟着这个选择走。
- **主连接一直都在**：键鼠、剪贴板、文件、控制消息永远走主连接，选的只是画面。画面走专线时其实两条线同时在用。
- **主连接自己内部还有一层选择**（直连 / 打洞 / 中继），RustDesk 已经做好、对我们透明，这里不管。
- 对比现在：现在是把两整条链路打包成「通用模式」「专业模式」两套，二选一；目标是拆成一条链路、逐环节选。

**按设备选**（看两头硬件，连接时定）：

| 环节 | 从好到差 | 依据 |
|---|---|---|
| 被控端采集 / 编码 | 显卡直采硬编 → RustDesk 视频服务 | 被控端系统和显卡 |
| 格式 / 颜色 | HEVC 4:4:4 → HEVC / H.264 4:2:0 → VP9 等；两头屏幕开着 HDR 时 10bit | 主控端能硬解什么、两头屏幕 |
| 主控端解码 / 上屏 | 硬解直接上屏 → 软解普通绘制 | 主控端显卡和桌面 |

**按网络选**（看连不连得通，连接时定）：

| 环节 | 从好到差 | 依据 |
|---|---|---|
| 画面走哪条 | 画面专线 → 主连接（它自己再按网络走直连 / 打洞 / 中继） | 被控端内网地址连不连得通 |
| 码率 / 帧率 | 画面专线给足（现在 30 Mbps、60 帧）→ 走主连接时用 RustDesk 自带的码率调节（`video_qos.rs`） | 画面走哪条 |
| 丢包补救 | 画面专线：重传补发 + 静止画面补成无损 → 主连接：照 RustDesk 原有处理 | 画面走哪条 |

**谁来定、什么时候定**：

- **连接时由主控端定一次**（照 Moonlight）：主控端带着自己的解码 / 显示能力去问，被控端按自己的编码能力答。
  现在专业模式的请求已经是这个形状（主控端带 `FormatCaps` / `DisplayCaps` 发请求，被控端在 `Accept` 里回定下的格式），要扩的是档位，不是机制。
- **中途不主动换档**：用户在公司就一直在公司、在外面就一直在外面，一次连接中途网络环境基本不变。
- **两种中途变化要接得住**（比 Moonlight 多做的）：
  - 画面专线中途断了：只把「画面走哪条」退到主连接，窗口不关、菜单不变（现在是整个退回通用窗口）；
  - 用户在菜单里改了会影响格式的设置（如悬浮球「HDR」）：被控端按新格式重建编码器（现在已经这样做）。
  主连接自己断了，RustDesk 本来就自动重连，重连时整套重新定一次。

**用户看到的**：一个窗口、一套菜单；质量面板照实写当前组合（如「UDP 直连 · HEVC 4:4:4」「中继 · H.264」），
不再有「专业模式 / 通用模式」的切换和「非专业模式：……」这类整体退回的提示。

## 7. 借鉴什么、保留什么

**从 Moonlight 借鉴**（必要时直接借代码，许可兼容）：主控端主导的连接时协商和编码排序；各平台「硬解 + 上屏」后端统一在一个接口后面；
原生会话窗口、统计面板由渲染器直接画；画面单独一条线；丢包的分层处理思路。

**保留我们自己的**：RustDesk 的中继 / 外网 / 受管 / 文件传输 / 剪贴板 / USB / 麦克风；悬浮球菜单（Moonlight 串流窗口没有菜单）；
静止画面补成无损、一键切 HDR、每块屏一个窗口、连接票授权。

**不换底座**：RustDesk 的功能两头都写在它的 Rust 协议上，搬到 Sunshine / Moonlight 是两头重写，不是照抄（2026-10-27 讨论过、用户定保持现状）。

## 8. 界面框架：用 Qt 统一全平台

**用户定（2026-10-27）**：要改就用 Qt 全平台统一一套界面和逻辑，不做「Linux 一个做法、Windows 一个做法」。

**前提**：主控端的远程会话窗口不能是 Flutter——Flutter 占着整个窗口的画布、外来画面只能当贴图，装不下直接上屏 / HDR 的画面，「一个窗口」做不到。
既然要换，就整体换成 Qt：会话窗口和首页 / 设置 / 文件传输等窗口都用 Qt（顺带解决 Windows 上字发虚：Qt 用系统渲染画字，Flutter 不支持 ClearType）。

| 层 | 统一成一份 | 仍按平台各写一份 |
|---|---|---|
| 窗口、菜单、悬浮球、多屏标签、弹窗、首页、设置、文件传输（Qt） | ✅ | |
| 会话逻辑：连接、协商、键鼠、剪贴板（RustDesk 的 Rust 核心，本来就跨平台） | ✅ | |
| 显卡硬解 + 直接上屏 + HDR | | Windows（D3D11）、Linux（VAAPI + Wayland）、Mac（VideoToolbox + Metal），藏在一个接口后面，Qt 上层只看到一块「画面区域」 |

这正是 moonlight-qt 的结构（界面和逻辑一份、解码上屏后端按平台分），它本身就是 Qt 写的，后端代码可以更直接地借。

- 现在 Linux 的专业窗口（Rust 写的 Wayland 窗口、tiny-skia 画的悬浮球）不再扩成会话窗口，而是作为 Linux 解码 / 上屏后端的素材并进 Qt 会话窗口；悬浮球改用 Qt 画。
- Rust 核心和 Qt 之间要接一层（cxx-qt 或 C 接口）；RustDesk 核心本来就是给不同界面接的（接过 Sciter 和 Flutter）。
- 授权：Qt 开源版 LGPL / GPL，和 RustDesk 的 AGPL 兼容，不用商业版。

## 8.1 顺序

每步做完都能用，可停在任何一步：

| 步 | 做什么 | 做完的标志 |
|---|---|---|
| 1 | **Qt 会话窗口**（全平台一份），先接 Linux 后端（瘦客户机是产品主力端，现有专业窗口的解码 / 上屏并进来），能显示画面专线和主连接两种来源的画面；菜单照通用控制中心（10-27 悬浮球菜单对齐就是在理清这份菜单） | 瘦客户机连任何工作站（内网 / 中继 / 对方不支持专业）都只出这一个窗口 |
| 2 | **补 Windows 后端**（D3D11 硬解 + 上屏），同一个 Qt 会话窗口 | Windows 主控端也只有一个会话窗口，内网时拿到和瘦客户机一样的画质 |
| 3 | **画面走哪条单独可退**：画面专线连不通或中途断了，只把画面改走主连接 | 防火墙挡掉画面专线后窗口不关、画面继续，面板显示走了主连接 |
| 4 | **被控端视频合成一套**：显卡直采直编变成 RustDesk 视频服务里「最好的那一档编码器」；格式可协商（支持 4:2:0） | 走中继时也用显卡直编；不支持 4:4:4 的主控端拿到 4:2:0 硬解画面而不是退回 VP9 |
| 5 | **首页 / 设置 / 文件传输等也换成 Qt**，Flutter 整体退出 | 程序里不再有 Flutter |

第 1 步做完之前一切照旧；第 1、2 步期间首页等窗口暂时还是 Flutter，会话窗口已是 Qt。

## 9. 代价和风险

- 体量：按月计，是目前讨论过的最大项目（换成 Qt + 两套视频合一）。Flutter 桌面界面约 6 万行 Dart（其中约 1 万行地址簿 / 原首页受管版不用，
  约 2 万行是逻辑层，键鼠输入最难）；受管版只做用得到的，估计实际要写 1.5–2 万行。
- 被控端视频服务会和 RustDesk 上游分得更开，每月合并上游更费事；需要在合并上游检查清单里加对应条目。
- 走中继时的画质受中继服务器带宽限制，码率上限要实测定。
- 原生窗口要自己做的东西：多屏标签、各种弹窗、键鼠、输入法等现在 Flutter 远程窗口里现成的，要逐项迁到原生窗口或悬浮球菜单。
