# 打包编译（DreamDesk 产品版）

首次搭环境（代理、镜像、Flutter 补丁、vcpkg、WSL 依赖）见仓库根 `BUILD-DEPLOY.md` §0–§3，本文只写日常命令。

| 平台 | 产物 | 状态 |
|---|---|---|
| Windows 客户端 | `dreamdesk-pro.exe`、`dreamdesk-pro-<版本>-install.exe` | 脚本一条命令 |
| Linux 客户端 | `dreamdesk-pro-<版本>.deb` | 脚本一条命令（2026-10-20 改名完成） |
| 服务端 | `hbbs`、`hbbr` | 上游原样 |
| macOS / iOS / Android | — | 环境未搭 |

开关：`dd-pro` 专业模式，`dd-brand` 产品改名（含只连内网的服务器预置）。都不开 = 上游 RustDesk。
`build.py` 的 `--dd-pro`、`--dd-brand` 把它们映射成编译开关（和 `--hwcodec` 等同一处）；Windows 上带
`--dd-brand` 的完整打包要走下面的脚本（它负责改名），直接用 `build.py` 打会被拒绝。

## Windows 客户端

```powershell
$env:PATH = "D:\WORKPLACE\CODING\_toolchain\flutter\bin;C:\Python312;C:\Python312\Scripts;$env:USERPROFILE\.cargo\bin;" + $env:PATH
$env:ALL_PROXY = "socks5h://127.0.0.1:10808"
$env:VCPKG_ROOT = "D:\WORKPLACE\CODING\_toolchain\vcpkg-rustdesk"   # 锁定版本 9e593bb 的 vcpkg，搭法见 BUILD-DEPLOY.md

cd D:\WORKPLACE\CODING\rustdesk
powershell -File dreamdesk\scripts\build-windows.ps1
# 默认带 --hwcodec --vram（与官方 Windows x64 发布版一致；专业模式的采集也要 vram）
```

- 产物：`flutter\build\windows\x64\runner\Release\dreamdesk-pro.exe`；安装包在仓库根。
- 脚本已包含 准备官方流程里 build.py 之外的三样（下载、编 WindowInjection）→ pub get → codegen →
  `build.py --dd-pro --dd-brand` 编 Rust 和 Flutter → 把三样放进程序目录 → 改名 → 打安装包 → 自检（有 `rustdesk*.exe` 就报错）。
  准备放在最前面：没开代理、缺 C++ 工作负载、打印驱动校验不过，几分钟内就报错，不用等完整编译。
- 「官方流程里 build.py 之外的三样」照官方 Windows 发布流程（`.github/workflows/flutter-build.yml`）做，地址、版本、
  编译参数从那份配置里读：隐私模式要的 `WindowInjection.dll`（从 RustDeskTempTopMostWindow 固定提交编，要装
  Visual Studio 的 C++ 工作负载）、虚拟显示器驱动 `usbmmidd_v2`、远程打印驱动（按官方校验文件校验，对不上就报错——
  官方是跳过，但缺了它就不是完整的包）；打安装器前和官方一样删掉清单里的 `dpiAware`（打完按原文件还原）。
  下载要能连 GitHub（`ALL_PROXY`），缓存在 `target\dreamdesk-deps`（校验文件 `sha256sums` 每次重下；校验不过的缓存会被删掉，重跑即重下）。
- 版本信息（文件属性里的产品名、原始文件名、描述）改成 DreamDesk / `dreamdesk-pro.exe`（用户 2026-10-23 定）：按原始文件名
  匹配的安全软件规则不会再把它当成 rustdesk.exe。主程序的写在 Flutter 的 `Runner.rc` 里，脚本编之前临时替换、打完按原字节还原
  （上游文件不改）；安装包的由打包器构建脚本按 `dd-brand` 开关设。公司名、版权行没改，还是 RustDesk 的。
- 和官方仍不一样的：不签名（没有官方证书）、不出 MSI；本机 C++ 部分（Flutter 外壳、插件、WindowInjection）用本机的
  Visual Studio 18 编，官方是 VS 2022（WindowInjection 工程指定 VS 2019 工具集，本机没装时脚本自动换本机工具集并在日志里写明）。

### 编译环境比官方新（用户 2026-10-19 定：保持新的，不降到官方版本）

| 项目 | 官方发布流程 | 本机 |
|---|---|---|
| Rust | 1.75 | 1.98 |
| Windows C++ 编译器 | VS 2022（WindowInjection 用 VS 2019 工具集） | VS 18 |
| Linux 编译系统 | Ubuntu 18.04 容器（glibc 2.27） | WSL Ubuntu 24.04（glibc 2.39） |
| Flutter、第三方库（vcpkg 锁定版本） | 3.24.5、9e593bb | 一致（Windows 2026-10-21 起；之前本机 Windows 一直用 `C:\vcpkg` 里 8 月装的 FFmpeg 7.1，锁定版本是 7.1.1） |

已知后果（接受）：
- Linux 包只能装在 glibc 2.39 及以上的系统（如 Ubuntu 24.04）；
- `WindowInjection.dll` 动态依赖 VC++ 运行库，用新工具集编，被控端的运行库要不旧于 VS 18 的版本，否则隐私模式开不了
  （Flutter 外壳、插件、Rust 部分都静态链接运行库，不受影响）；
- 我们的专业模式代码只在 Rust 1.98 上编过，没查能否用官方的 1.75 编。
- 换过 VS 版本后报 `generator ... does not match`：先 `Remove-Item -Recurse -Force flutter\build\windows`。

## Linux 客户端（本机 WSL Ubuntu 24.04）

```bash
wsl -d Ubuntu-24.04 -u root          # 一定要 root：工具链都装在 /root 下
cd /root/rustdesk
git fetch /mnt/d/WORKPLACE/CODING/rustdesk dreamdesk && git checkout -f -B dreamdesk FETCH_HEAD
git submodule update --init --recursive

. ~/.cargo/env
export VCPKG_ROOT=/root/vcpkg PATH=/root/flutter/bin:$PATH
# vcpkg.json 变了才需要：
# $VCPKG_ROOT/vcpkg install --triplet x64-linux --x-install-root=$VCPKG_ROOT/installed

bash dreamdesk/scripts/build-linux.sh
# 产物：/root/rustdesk/dreamdesk-pro-<版本>.deb（约 2–3 分钟，增量）
```

- 脚本做的：pub get → codegen → 按 build.py 的开关表（`--flutter --hwcodec --dd-pro --dd-brand`）编 Rust → build.py 编完
  Rust 做的同一处修正 → 编 Flutter → 改名打包（见下面「Linux 改名方案」）→ 自检。带 `--dd-brand` 直接用 build.py 打包
  会被拒绝（打出来的包名、程序、服务都叫 rustdesk，和运行时的应用名对不上）。
- 装：`apt-get install ./dreamdesk-pro-<版本>.deb`。包声明和 `rustdesk` 互斥、可替换它，装的时候 apt 自动卸掉 rustdesk
  （包括我们以前的测试包）。
- 包的版本号是「程序版本 + 构建时间」，如 `1.5.1+202610231105`（用户 2026-10-23 定）：程序版本跟着上游几个月才变一次，
  版本号不变时 apt 会把新构建当成「已是最新」跳过；带构建时间后每次构建都比上一次新，直接 `apt-get install` 就能升级。
  文件名也带它，脚本打完只在仓库根留最新的一个包。
- 不要专业模式、也不改名：直接 `python3 build.py --flutter`（上游原样，包名 rustdesk）。
- 打出的包依赖较新的 glibc（见 `BUILD-DEPLOY.md` §3），老系统装不上。

### Linux 改名方案（2026-10-20 写成，用户同日确认；和 rustdesk 包互斥，装新包自动卸旧包）

**问题**：带 `--dd-brand` 打出的包，程序运行时自称 `dreamdesk-pro`（配置、日志、IPC 目录、服务名、进程匹配、链接协议
`dreamdesk-pro://`、快捷键授权的应用名都按它派生），但包名、程序文件、服务、桌面文件、图标都还叫 `rustdesk`，内外对不上：
`systemctl … dreamdesk-pro` 找不到服务，按 `dreamdesk-pro --server/--tray` 找进程找不到，`dreamdesk-pro://` 链接没人接，
GNOME 按 `dreamdesk-pro` 记的快捷键授权（RustDesk 设置页「清除快捷键授权」也按它找）对不上实际的桌面文件。官方 Linux 发布流程没有改名机制
（Windows 有 RDAPPNAM 模板，Linux 没有）。

**做法**（照 Windows：只给程序文件和安装包改名，内部库名不动，其余靠运行时应用名派生，最后用文件名检查兜底）：
1. 新脚本 `dreamdesk/scripts/build-linux.sh`：codegen → 从 `build.py --flutter --hwcodec --dd-pro --dd-brand --print-features`
   取编译开关，照 build.py 在 Linux 上的同样命令自己跑 cargo 和 flutter（不让它打包；编完 Rust 后那条修生成桥接的 sed 是从 build.py
   抄的，上游改了要跟着改）→ 程序文件 `rustdesk` 改名 `dreamdesk-pro`（GTK 按程序文件名定窗口的应用名，进程名也跟着变）→
   用上游 `res/` 里的模板替换出我们的安装包文件 → 打 `dreamdesk-pro-<版本>.deb`（先打在临时目录）→ 自检过了才放到仓库根。
   替换是对这几个模板做全文的 `RustDesk` / `rustdesk` 替换；模板里一出现网址（`rustdesk.com`、github 等）脚本就停下，
   要先改成按行区分，免得网址被一起换掉。
   上游改了模板，下次打包自动带上。
2. 安装后的样子：包名 `dreamdesk-pro`；程序 `/usr/share/dreamdesk-pro/dreamdesk-pro`，`/usr/bin/dreamdesk-pro`；
   服务 `dreamdesk-pro.service`；桌面文件 `dreamdesk-pro.desktop`（StartupWMClass、Icon 都是 dreamdesk-pro）；
   链接协议 `dreamdesk-pro-link.desktop` 注册 `x-scheme-handler/dreamdesk-pro`；图标 `hicolor/*/apps/dreamdesk-pro.*`；
   root 服务配置 `/root/.config/dreamdesk-pro`。内部库 `librustdesk.so` 和入口符号不改（Windows 也保留 `librustdesk.dll`）。
3. 代码里写死、必须跟着改的两处（`dd-brand` 门控，不开产品开关时照旧）：
   - D-Bus 名 `org.rustdesk.rustdesk`（链接转发给已运行的实例靠它）：产品版用自己的名字，不和原版 RustDesk 抢；
   - 专业窗口的应用名（今天为了共用快捷键授权写死成 `rustdesk`）：改成跟应用名走（`dreamdesk-pro`）。
   Flutter 外壳里按名字找窗口图标那一处（`my_application.cc`）只影响 X11 下的窗口小图标，Wayland 下 GNOME 用桌面文件的
   图标，不改。
4. `build.py` 加一道拦截：Linux 上带 `--dd-brand` 直接用 build.py 打包就报错（和 Windows 那道一样）。
5. 自检：打出的包里不许有名字带 `rustdesk` 的程序、服务、桌面文件、图标（`librustdesk.so` 放过）；control 的包名必须是
   `dreamdesk-pro`。

**验证**：`dpkg -c` 列文件名逐项核对（机器）；瘦客户机卸掉旧的 `rustdesk` 测试包、装新包：`systemctl status dreamdesk-pro`、
进程名、`--server/--tray` 找得到、`xdg-open dreamdesk-pro://…` 有实例接、专业模式照常、快捷键不弹框（机器 + 日志）；
托盘图标、开始菜单里的图标和名字（人眼）。

**实施结果（2026-10-20）**
- 打包：WSL 里约 140 秒（增量）；包内程序、服务、两个桌面文件、图标都是 dreamdesk-pro，只有内部库 `librustdesk.so` 保留；
  自检通过。踩到一处：工作区从 Windows 拷进 WSL 的文件带 CRLF，从 build.py 读依赖列表时行尾多回车没匹配上 → 脚本读依赖
  和替换模板时都去掉行尾回车（模板带回车装出去的桌面文件、服务文件也会出问题）。
- 瘦客户机换装：apt 自动卸掉旧的 rustdesk 测试包（只留配置记录 `rc`）；`dreamdesk-pro` 服务运行并开机启动；被控端进程名
  `/usr/share/dreamdesk-pro/dreamdesk-pro --server`（按进程名找得到了）；`/usr/bin/dreamdesk-pro`、两个桌面文件到位；
  `dreamdesk-pro://` 由 `dreamdesk-pro-link.desktop` 接管。
- **还没验**（瘦客户机当时被切回旧客户端，没有 GNOME 桌面）：连接后专业模式和悬浮球、快捷键不弹框、D-Bus 名、托盘和开始菜单
  里的图标和名字。
- 安装包维护者一栏先写了 `DreamDesk <dreamdesk@of3d.com>`，邮箱是占位的，待用户给真实地址。

## 注意

- 构建会改写 `flutter/pubspec.lock`，提交前 `git checkout -- flutter/pubspec.lock`（Windows 脚本按改前的原字节自动还原，不丢本地改动）。
- 公司电脑上不能运行名叫 `rustdesk.exe` 的程序（IT 黑名单，会被结束并删除）；上游原样的测试版要改名再跑。

## 审查：打包脚本、安装动作、Flutter 侧改动（2026-10-23 凌晨，夜间只读审查）

已修（都真跑验证过）：
- Windows 脚本找不到某个工具（比如没装 `flutter_rust_bridge_codegen`）时只记一条错误、退出码还是上一条的 0，会接着用旧的生成文件打包：
  调用前先放一个哨兵退出码，并显示 PowerShell 自己的错误原话。
- 自检排在生成安装包之后，查出问题时坏包已经覆盖了上一个好的：Windows 自检挪到打安装包之前；Linux 先打在临时目录、自检过了才放到仓库根。
- 打包结束用 `git checkout` 还原锁文件会丢本地未提交的改动：改成和清单文件一样按原字节还原。
- Windows 脚本补上程序名和 `brand.rs` 一致的检查（Linux 早就有）。
- 程序内升级是合并复制、不删旧文件，换 usbip-win2 版本后目录里会有两个安装程序，原来直接报错、驱动永远升不上去：取版本最高的。
- 本文档 Linux 改名方案里两处和脚本不符的描述改正。

待用户定（产品取舍）：
- deb 版本号就是上游的 1.5.1，每次构建都一样：`apt-get install` 新构建可能被当成「已是最新」跳过（我们的安装脚本带 `--reinstall` 所以没撞到）。
  可以加单调递增的后缀（如 `1.5.1+dd<日期时间>`）。
- 机器上原先就有别人装的 usbip-win2 时，产品会接管它（隐藏、按随包版本覆盖、关自动重连），产品卸载时一并卸掉。
  可以只在我们真装过时写归属标记，卸载和隐藏看标记（约 15 行，要在虚拟机里验，不能用 209.32）。
- 程序和安装包的版本资源（原始文件名、产品名）还是 RustDesk：按「原始文件名」匹配的安全软件规则会把 `dreamdesk-pro.exe` 当成
  `rustdesk.exe`，任务管理器里也显示「RustDesk Remote Desktop」。改要动打包流程（中等工作量）。

待白天人眼验：通用窗口里专业模式标签上的按钮外面套着把点击转发给远程的那层，点「重新进入专业模式」时远程左上角也收到一次点击（修法 1 行）。
会话的提示状态在 Dart 侧永不清理，每次连接多一条很小的记录（不影响功能）。
