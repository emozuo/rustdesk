## 1. USB 透传（2026-10-22，用户确认方案和下面 4 条决定）

### 要解决什么

CG 制作人员天天用数位板。原项目 2026-10-14 起数位板改走 USB 透传：被控端装厂商驱动，笔键自定义、Wintab 压感、
按软件分配置原样可用（之前「主控端采集、被控端合成笔输入」的做法拿不到这些，放弃了）。RustDesk 没有任何 USB 透传
（`src`、`libs/base`、`flutter/lib` 里搜不到），也没有数位板压感；外设只有「看被控端摄像头」「被控端打印到主控端」
「语音通话（声音只在被控端播放）」这几样。

### 用户定的决定

1. 先只透数位板，自动、无勾选（加密狗、3D 鼠标等要选择界面的，放到 UI 重规划）。
2. 产品版主控端默认每次连接都自动送走数位板（关闭开关放到 UI 重规划）。
3. 被控端跟随 RustDesk 已有的「键盘鼠标控制」权限：没有键鼠控制权（只看、或连接管理窗口里关掉），数位板不透，
   留在主控端本机当鼠标用；现在不加界面。
4. 放弃「合成笔」路线（架构文档的 `ddpro-pen`），数位板全走 USB 透传。代价：目前只覆盖 Linux 主控端 → Windows
   被控端，Windows / Mac 主控端用数位板到 P3 再定。

### 为什么不用 RustDesk 的 TCP 隧道（端口转发）

- 方向反：它是主控端本机监听、被控端去连被控端网络里的地址（`src/port_forward.rs`、`connection.rs` 的端口转发）；
  USB/IP 是被控端的导入方（usbip-win2 驱动在内核里用 WSK 主动连）去连主控端的导出方。
- 它是另一条连接、单独登录（`ConnType::PORT_FORWARD`），多路复用只在端口转发连接上生效，已有的远程桌面会话里
  不能由程序开通道；权限语义也是「访问被控端网络」。

### 方案

USB/IP 原始字节流放进远程会话那条连接里的专业协议信封（`bytes dd_pro`）转发：加密、鉴权、穿透、中继都是 RustDesk 的，
两种模式都能用，不开任何新的网络端口。

- **主控端（Linux 瘦客户机）**：会话进程按原项目实测的判据认出 USB 数位板（有笔节点、USB 总线），把「要透的设备全集」
  发给被控端；被控端驱动来要设备时（隧道里第一个报文是导入请求），请 root 服务把设备从本机驱动解绑、绑到内核
  `usbip-host`，并把一对本机套接字的一端写进 `usbip_sockfd`，另一端和隧道对接。**不用 usbipd、不开 3240 端口、
  不要和内核版本绑死的 `linux-tools`**（原项目内核一升级透传就坏），只用内核基础包里的 `usbip-host` 模块
  （.165 上属于 `linux-modules-7.0.0-38-generic`）。
- **root 端点**：在 root 的 `--service` 里开专用 Unix 套接字，照 RustDesk `_drm` 的写法（`src/ipc/drm.rs`）：授权用
  `ipc/auth.rs` 的 `authorize_service_scoped_ipc_connection`（只认当前活动会话用户的同一个程序），套接字随 SCM_RIGHTS
  传过来。只有绑定 / 交套接字 / 收回三个操作，数位板判据在 root 里再校验一遍；按 IPC 连接记账，连接一断（会话结束、
  会话进程崩溃）立刻收回、还给原驱动、清 `match_busid`。
- **被控端（Windows，`--server` 以 SYSTEM 跑）**：检查键鼠控制权限和驱动；开一个只监听 `127.0.0.1` 的临时端口、
  只收一个连接，`usbip.exe -t 端口 attach -r 127.0.0.1 -b BUSID --terse` 让驱动连上来，之后双向搬运字节。会话结束、
  权限收回、主控端撤下设备时主动断开（实验 E3：一断开 Windows 侧设备就消失，没有残留和重连）。
- **协议**：专业协议 v10 新增 `UsbOffer`（设备全集）、`UsbStatus`（挂上 / 被拒 / 撤下 + 原因）、`UsbOpen` / `UsbData` /
  `UsbClose`（一条流的开、数据、关；每次挂载新流号，旧流晚到的数据串不进来）。
- **专业模式配套**：笔挪的是被控端的光标，专业窗口现在只跟随本机鼠标；要补「被控端光标被别的东西挪动时，专业窗口
  画出远程光标」，否则专业模式下用笔看不到光标。通用模式 RustDesk 已经会处理。

### 原项目做法逐条审查（结论）

| 原做法 | 结论 |
|---|---|
| 主控端 `usbipd` 监听 3240 + nftables 只放行被控端，明文 | 不要了：自己应答握手、走加密的会话连接，没有监听端口 |
| 依赖 `linux-tools-$(uname -r)`（usbip 工具） | 不要了：只用内核模块；省掉为它补的安装 / 升级脚本和告警 |
| 数位板判据（笔节点、USB 总线、蓝牙板不认；修过误导出手柄 / 3D 鼠标）、2 秒扫一次 | 保留，root 里再校验一遍 |
| 拔掉后清 `match_busid` | 保留（不清的话那个 USB 口以后插什么都被 usbip-host 抢走） |
| 停止时收回 usbip-host 下所有设备、杀 usbipd | 收窄：只收回本端点绑的，按 IPC 连接记账 |
| 被控端每 3 秒 `usbip list -r` 对账 | 不轮询：主控端主动发设备全集 |
| 被控端从不主动卸载（「切分辨率会重连」） | 前提不成立（RustDesk 改分辨率不重连）：会话结束 / 权限收回时主动断开 |
| usbip-win2 锁版本 + sha256、只装 `main,client`、隐藏、按卸载登记判已装 | 保留；版本见下 |

### 驱动选型（usbip-win2）

在「被控端要用厂商驱动」的前提下（笔键自定义、Wintab），只能在 USB 层透传。可选：usbip-win2（开源、微软签名、免费，
主控端用内核自带模块零维护，协议公开能放进我们的加密连接）；VirtualHere / FlexiHub 等商业产品（按台收费、闭源、
自有协议和端口，难以放进加密连接）；自己写虚拟 USB 驱动（工作量和签名门槛不现实）；只模拟成标准 Windows 数位板
（没有往返限制，但厂商驱动认不到，原项目因此放弃）。**选 usbip-win2。**

版本：0.9.7.8 有蓝屏，排除。0.9.8.0（2026-09-07）是实验用的版本，新增低延迟收包模式，已知回归是「DPC 级别提交的
OUT 传输失败」（USB 网卡、手柄耳机，issue #190）。0.9.8.1（2026-09-27）修了它、驱动拿到微软硬件认证，但作者自称
「AI 辅助审查约 100 个提交，可能有回归」，有未解决的「装上后 Windows 不睡眠」（#197）。**锁 0.9.8.0**：实验、压测都在它上面跑；
升 0.9.8.1 要把透传压测重跑一遍（它修好的「停止重连」能消掉下面打包一节的窗口期）。

### 实验（2026-10-22，脚本在会话草稿目录，不进仓库）

瘦客户机 .165（内核 7.0.0-38，Wacom Intuos M 056a:0375 在 1-1）↔ 209.32（usbip-win2 0.9.8.0，原项目装的）。

- **E1 自应答握手 + 本机套接字对**：瘦客户机小程序收 40 字节导入请求，绑 usbip-host，把 AF_UNIX 套接字对一端写进
  `usbip_sockfd`（`usbip_status` 1 → 2），回 320 字节导入应答，另一端和 TCP 互相搬运。209.32 `attach` 成功，Wacom 的
  数位板 / 笔 / 鼠标 / 厂商设备全部 OK。坑：设备从本机驱动解绑后 `bConfigurationValue`、`bNumInterfaces` 读出来是空的，
  设备信息要在解绑前读。
- **E2 被控端回环中转**：209.32 上只监听 `127.0.0.1` 的中转口，驱动经 WSK 连回环地址，`--terse` 直接给端口号，挂载 OK。
- **E3 断开语义**：中转一断，Windows 侧设备立即消失、`usbip port` 为空；瘦客户机侧设备回到本机驱动，笔和触控区两个 input
  节点都回来。（当时只看了断开那一刻，结论「没有重连尝试」是错的：驱动 30 秒后才开始后台重连，见下面「驱动卡死事故」。）
- **E4 采样率与往返**（用户在板子上连续画圈）：本机 evdev 每秒 133 个报告；透传后每秒 133（30 秒每秒都是 133–134），
  「返回发给被控端 → 同一端点下一个提交」p50 0.74 ms、p95 1.54 ms。被控端同一端点同时只挂 2 个读请求（应是 Windows
  自带 HID 驱动的行为，任何在 USB 层透传的方案都一样），所以**往返 ≤ 约 15 ms（两个报告间隔）时采样率不掉，超过后约为
  2 ÷ 往返**。瘦客户机出方向人为加延迟验证：+10 ms 每秒 133（不掉）、+30 ms 每秒 62（约一半），和推算一致。
  结论：内网、同城放心用；通用模式下笔数据和画面排在同一条连接里多出的几毫秒在余量内，不需要另开直连通道；跨地区外网
  先不承诺数位板。外网的办法以后做「预读」（主控端中转连续读设备、被控端中转从本地队列应答驱动的读请求），不换驱动。

### 分步实施

1. 协议（v10）和新 crate `ddpro-usb` 骨架；Windows / Linux 上 feature 开关两种 `cargo check` 都过。
2. Linux 纯逻辑：认数位板、USB/IP 握手报文、usbip-host 的 sysfs 操作。判据：.165 上只列出 Wacom，握手字节布局和 E1 一致。
3. root 端点（`--service` 里），复用 RustDesk 的授权。判据：别的用户 / 别的程序连上来被拒。
4. 被控端：按连接的挂载编排、`connection.rs` 的薄钩子（权限、连接关闭）。
5. 主控端编排并端到端联调：连上 5 秒内 209.32 出现 Wacom；断开 3 秒内两端恢复；`kill -9` 主控端程序 2 秒内设备回本机；
   关掉键鼠控制 1 秒内撤下；被控端没装驱动时日志写明、数位板留在本机。
6. 专业窗口跟随远程光标。
7. 打包：Windows 安装包带锁版本的 usbip-win2（定 0.9.8.0 还是 0.9.8.1）；deb 检查 usbip-host 模块。
8. 人工验收：压感、倾斜、笔键、Wintab 程序、锁屏和 UAC 界面下用笔。

### 实施进展（2026-10-22）

- 第 1–3 步：协议 v10、新 crate `ddpro-usb`（握手报文、认数位板、usbip-host 的 sysfs 操作、传描述符、root 端点和客户端、
  被控端调 usbip-win2）。.165 上只认出 Wacom（键盘、鼠标、USB 声卡不认）；root 端点权限分离验证：普通用户直接绑被拒（权限不足），
  经端点绑定、交套接字、挂到 209.32、收回都成功；客户端不收回直接退出，端点立刻收回、状态文件清空。
- **收回顺序的坑**：只写 `del` 清不掉 `match_busid` 登记（解绑后处在「已登记、未绑」状态，内核只标待删），照 Linux 自带
  `usbip unbind` 改成「解绑 → del → 写 rebind」，登记才真删；不清的话这个 USB 口以后插什么都被 usbip-host 抢走。
- 第 4–5 步端到端：瘦客户机连 209.32，从会话建立到被控端挂上数位板不到 1 秒；正常断开 3 秒内、强杀主控端进程 2 秒内
  数位板回到本机、内核登记和状态文件清空、209.32 无残留；被控端没装驱动（临时改名 usbip.exe）时被控端回「拒绝：驱动未安装」，
  数位板留在本机。关掉键鼠控制权的验证要在 209.32 的连接管理窗口里手动点，留给用户验收。
- 第 6 步：专业窗口收到被控端「被别的东西挪动」的光标位置（被控端只报不是本连接挪的）时，用叠加图层画出远程光标、藏起本机指针；
  本机鼠标一动换回。切换时写一行日志，供现场排查。
- **驱动卡死事故**：反复挂载、断开、强杀之后，209.32 上 usbip-win2 卡死（`usbip.exe` 报找不到虚拟控制器，重启设备挂住，
  Windows 重启卡在关机，断电后恢复）。原因在我们的用法：每次挂载换一个临时端口，每断一次驱动就在后台起一串连不上的自动重连
  （默认 20 次、约 2 小时），越积越多；代码里「结束时停止重连」在 0.9.8.0 有已知缺陷、调用直接失败，没起作用；0.9.8.0 还有
  「挂载任务互相等待、卡住驱动卸载」的问题（#188，之后的版本修了）。原项目总是连同一个地址（对端:3240），每块设备最多一串重连，
  碰巧没有这个问题。修法：驱动的 `ReattachMaxAttempts` 设 0（驱动文档支持，驱动加载时读；209.32 已设、重启后生效），
  安装包装驱动时设、被控端首次使用时再查一遍兜底；调 usbip.exe 的每条命令加 15 秒超时（原项目是 10 秒），驱动出问题时不跟着挂死。
  和原项目逐条比：传输加密、不开端口、不依赖内核工具包、事件驱动不轮询、会话结束主动拔下——新做法更好；驱动自动重连和命令超时
  这两处原项目做对了（前者是碰巧），已补上。
- **修补后压测**（209.32 断电重启、`ReattachMaxAttempts=0` 生效后）：8 轮「连上 → 正常关（偶数轮）/ 强杀主控端会话进程（奇数轮）」，
  每轮连上后数位板都透过去、被控端每次都挂在 1 号端口（驱动每次都干净地放开了端口）；强杀后 2 秒内、正常关后 3 秒内数位板回到本机，
  内核登记和状态文件清空；最后一轮断开 30 秒以上（驱动原本开始后台重连的时间）之后再连照常挂上，被控端日志没有失败、超时。
- **第 7 步打包**：打包脚本下载 usbip-win2 官方安装程序（锁版本 + sha256，核对发布者签名），原样放进程序目录的 `usbip\`；产品安装
  （含升级）时跑 `dreamdesk-pro.exe --ddpro-usbip install`：已是同版本就不动，否则静默装（只装驱动和命令行、不建快捷方式），
  在「程序和功能」里藏起来（它跟着产品走），装前装后都把 `ReattachMaxAttempts` 设 0；真卸载产品时（和打印机驱动同一个判断）
  `--ddpro-usbip uninstall` 带走它。瘦客户机 deb 不用改：usbip-host 在内核基础模块包里。209.32 上用正式包覆盖安装：
  usbip-win2 0.9.8.0 装上并隐藏、重连次数 0、没有快捷方式，瘦客户机连上后数位板挂到 209.32。卸载这条路径还没实测。
  - 坑：远程装测试包时，安装包是自解压壳、几秒就退出，真正的安装是它解压出的 `--silent-install` 进程，再往下才是装驱动；远程会话
    在这之前断开会把它们一起杀掉（第一次就这样把 usbip-win2 装坏了一半）。远程装要等这一串进程都结束；用户双击安装没有这个问题。
  - 已知限制：usbip-win2 的安装程序会把重连次数复位成默认，驱动又只在加载时读这个值，所以**第一次装上到被控端下次重启之间**
    驱动自动重连仍开着。卡死要几十轮连断才积累出来，正常使用无碍；安装后重启驱动正是之前卡住过的那一步，风险更大，不做。
- 还没做：第 8 步人工验收（压感、倾斜、笔键、Wintab、锁屏和 UAC 界面下用笔，专业模式下悬停看得到光标，关键鼠控制权后撤下）。
- **代码审查**（2026-10-22，独立审查代理 + 自查）发现并修掉：
  1. root 端点的状态文件原来放在 /tmp 下的套接字目录、先读写后查目录、写时跟随符号链接——那个目录在 RustDesk 收归 root 之前
     可能被普通用户抢建并放好指向系统文件的链接，root 一写就覆盖。改为放在 root 自建的 0700 目录 `/run/ddpro-usb/`
     （开机清空，和内核登记同生命周期），套接字目录不跟随符号链接地检查、等 RustDesk 收归 root 后才往里放东西。
  2. 设备从本机驱动解绑之后的出错路径不收回（本机整个会话都用不了数位板）：root 端 BIND 失败就地收回并撤所有权；
     会话端绑上之后任何错都收回。
  3. 被控端在 RustDesk 的异步连接循环里做阻塞操作（首次清理跑注册表和驱动命令、持全局锁写驱动套接字），驱动一卡所有连接的
     透传、权限切换、连接关闭都卡死：首次清理放进线程（清理完再对账，免得拔掉刚挂上的），每条流一个写线程（消息循环只往队列里放，
     写有 5 秒超时）。
