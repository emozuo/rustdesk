# RustDesk 开发指南（AGENTS.md 中文译本）

> 译自仓库根目录 `AGENTS.md`（上游提交 `4812a9815`，2026-09-28）。**以英文原文为准**；原文更新后本译本可能过时。

## 项目结构

### 目录

* `src/`：Rust 主程序
* `src/server/`：音频 / 剪贴板 / 输入 / 视频 / 网络
* `src/platform/`：平台相关代码
* `src/ui/`：旧版 Sciter 界面（已弃用）
* `flutter/`：当前界面
* `libs/hbb_common/`：与服务端共用：rendezvous 协议、套接字、`Config` 核心
* `libs/base/`（crate 名 `base`）：仅客户端用：选项键、消息协议、文件传输、平台代码
* `libs/scrap/`：屏幕采集
* `libs/enigo/`：输入控制
* `libs/clipboard/`：剪贴板
* `libs/base/src/config/keys.rs`：所有选项的唯一导入路径

### 关键组件

- **远程桌面协议**：自定义协议，实现在 `src/rendezvous_mediator.rs`，用于和 rustdesk-server 通信
- **屏幕采集**：各平台的屏幕采集在 `libs/scrap/`
- **输入处理**：跨平台输入模拟在 `libs/enigo/`
- **音视频服务**：实时音视频流在 `src/server/`
- **文件传输**：安全文件传输实现在 `libs/base/src/fs.rs`

`hbb_common` 是与服务端共用的 git 子模块，改它要多走一轮（两边都得改）。仅客户端用的代码放进
`libs/base`，它是普通的 workspace 成员。`base::config::keys` 重新导出了 `hbb_common` 仍在读取的那几个键，
所以调用方从这一个路径就能拿到全部选项键。

### 界面架构

- **旧界面**：基于 Sciter（已弃用），文件在 `src/ui/`
- **新界面**：基于 Flutter，文件在 `flutter/`
  - 桌面端：`flutter/lib/desktop/`
  - 移动端：`flutter/lib/mobile/`
  - 共用：`flutter/lib/common/` 和 `flutter/lib/models/`

## Rust 规则

* 生产代码里避免 `unwrap()` / `expect()`。
* 例外：
  * 测试；
  * 获取锁时——那里失败意味着锁中毒，不是正常控制流。
* 其余情况优先用 `Result` + `?`，或显式处理。
* 不要静默忽略错误。
* 避免不必要的 `.clone()`。
* 能借用时优先借用。
* 非必要不加依赖。
* 代码保持简单、符合惯用写法。

### 日志

* `debug` 及以上级别会写进日志文件。可能反复触发的日志调用（每个包、每帧、每个输入事件、每轮循环，
  或者触发频率由对端控制）不许不加节流地用 `debug` 或更高级别。
* 这类调用点二选一：
  * `log::trace!`：事件是预期内的，这行日志只在主动调试时有用；
  * `hbb_common::throttled_log!(interval, level, ...)`：它表示一个故障，仍应出现在用户的日志里。
    每个间隔只留一行，并附上其余被压掉的次数。只有当节流判断要驱动不止一条日志调用时，
    才直接用 `hbb_common::log_throttle::LogThrottle`。

## Tokio 规则

* 假定 Tokio 运行时已经存在。
* 绝不创建嵌套的运行时。
* 绝不在 Tokio / 异步代码里调 `Runtime::block_on()`。
* 不要把运行时的创建藏在辅助函数或库里。
* 不要跨 `.await` 持有锁。
* 优先用 `.await`、`tokio::spawn`、channel。
* 阻塞工作用 `spawn_blocking` 或专用线程。
* 异步代码里不要用 `std::thread::sleep()`。

## 改动规范

* 只改必须改的。
* 优先最小的有效 diff。
* 不要重构无关代码。
* 不要做纯格式化的改动。
* 命名和风格与周边代码保持一致。

### 导入

* 每个 crate 一条 `use`。一个文件从同一个 crate 取的所有东西放进一个花括号块，不要一项一条语句：

  ```rust
  // 不要
  use base::fs;
  use base::message_proto::*;

  // 要
  use base::{fs, message_proto::*};
  ```

* 唯一可以拆开的理由是某个 `#[cfg(...)]` 不适用于整块——属性只绑定一个条目，所以门控条件不同的导入
  必须单独成行。`pub use` 重新导出同样不能和普通 `use` 合并。

  ```rust
  #[cfg(not(feature = "flutter"))]
  use base::fs;
  use base::message_proto::*;
  ```

* 因为部分条目挪到了另一个 crate 而要拆一条现有的 `use` 时，把两边各自并入对应 crate 已有的那一块，
  不要留下第二条语句。

### 注释

* 避免写注释，除非它解释的是不明显的原因、约束或变通做法。
* 绝不复述代码在做什么；与其写注释，不如把代码写清楚。
* 代码本身一目了然时，不加注释。

### 尽量少侵入（Be minimally invasive）

* 优先纯增量的改动：在现有代码外围加一层新的（`#[cfg]` 门控的）代码块或新函数，而不是重组现有代码。
  一个修复最理想的 diff 是只加行、不改不删。
* 不要为了让新代码能接上而抽取或重塑现有代码；找一种不动现有行的机制（例如隐藏 / 显示一个已有对象，
  而不是把它的构造过程重构成一个辅助函数以便重建）。
* 宁可接受一点重复，也不要重组。一个新函数重复已有函数里的几行，比把原函数改造成两者共用要好。
* 新逻辑放在它所属模块里的自包含函数中（平台相关逻辑放 `src/platform/`，`use` 写在函数体内部，
  以免搅动共享的导入块）。共享文件（`src/tray.rs`、`src/core_main.rs`、`src/server/connection.rs` 等）
  里的调用点应当是很薄的单行钩子。

### 动共享代码之前先查范围

* 改共享 trait、共享结构体或广泛使用的函数签名之前，先查这个 bug 或功能是否只属于某一条路径。
  如果是，就把改动限制在那条路径里，除非做不到；做不到时要在 PR 里说明原因。
* 如果某个无关调用方只是为了满足你改过的签名，就要传 `Default::default()`、`None` 或别的占位值，
  说明 diff 太宽了：停下来重新设计。
* 一个修复预期的形态是：功能自己模块里的一个新函数，加上它所需共享代码里最多一个新字段或一个薄钩子。
  功能专属的状态应放在该功能已有状态的旁边，而不是放进一个每个调用方都得去学的新抽象里。

### 必做的回归面检查（Mandatory regression-surface check）

在认为任何实现完成之前，对最终 diff 做一遍最小化检查。

* 检查每个被修改的已有文件和每条被修改的已有代码路径。每一处都必须是本次需求严格必需的。
  属于顺手清理、重构、一致性改进或修复既有问题的改动，一律撤回。
* 新功能在关闭或不支持时，只要可行，就保留原有实现路径。`feature off` 应当跑旧代码，
  而不是一个改写过的等价实现。
* 不要只为了和新功能共用代码，就把现有行为改走一个新抽象。宁可写一个并行的新函数或接受少量重复，
  也不要改动一条经过验证的现有路径。
* 新的实现逻辑放在新模块或功能专属模块里。对共享 / 核心文件的改动通常应该只是薄钩子、能力检查或协议接线。
* 不要在同一个 PR 里修无关的既有 bug。把它们放进单独的改动，除非它们直接阻碍本次工作的正确性或安全性。
* 子模块升级时，检查确切的提交区间，确保没有把无关改动带进父 PR。
* 定稿前，明确报告回归面：列出行为发生变化的已有文件和已有运行时路径，并解释每一处为什么不可避免。
* 评审时，一条被不必要修改的旧路径就算一条评审意见，即使测试通过、改写后的行为看起来等价。

### 评审中提出的边角情况

为覆盖一个边角情况而加的重构很少能收敛。每个新的计数器、时间戳、缓存或淘汰 / 过期规则都会和现有代码
依赖的状态相互作用，下一轮评审又会找出它带来的新问题。

* 修复简单且低风险时，边角情况仍然值得修：几行的局部改动，不加状态、不改已有的查找逻辑，
  例如挪动一处检查，或更早地拒绝非法输入。
* 唯一的修法需要新状态、新的生命周期规则或重组，而代码在那里已经能干净地失败、或者行为与 master 一致时，
  就在 PR 里把它写成已知限制。凡是超出简单修复的，都要先得到维护者的明确同意。
* 在加入会重排、过期或复用已有数据的状态之前，列出所有读取这份数据的查找逻辑，逐一确认它们仍然成立。
* 优先干净的失败（操作报错），而不是一套试图让罕见情况也成功的机制。
* 任何评审者给出的严重级别标签（P1、Critical、Major）都不是分诊结论。按后果套用下一条规则，而不是按标签。
* 需要新状态才能修的边角情况，只有在它会导致崩溃、丢数据、削弱安全性，或已有用户报告时才修。
  罕见的外观或布局小故障（例如拖动过程中旋转屏幕、默认关闭的功能）算已知限制：回复一次，
  在 PR 正文的「Known limits」下列出，代码不动。
* 如果某条意见针对的是本 PR 较早一次提交引入的行为，修法是删掉或简化那次提交，而不是在上面再加一层。
* 按所有轮次累计来判断增长，而不是按单轮。如果评审后续改动让非测试 diff 增长超过首次修复的一半，
  或者引入了新的一类状态（指向另一个组件的句柄、跨组件引用、延迟 / 帧后回调、定时器、缓存、标志位），
  推送前先停下来问维护者。
* 在某个罕见情况下很难保留用户偏好的状态时，退回到一个由当前输入算出来的确定性默认值。
  不要为了保留偏好而跨组件或跨帧协调可变状态。

## 测试

* 一个修复只为被报告的行为加回归测试：在 master 上失败、加了修复后通过。一到三个测试是常态。
* 断言用户看到的东西或 API 的返回值。不要测试私有状态、算法执行步骤的顺序，或评审中提出的每个边角情况。
* 修 bug 时不要加测试基础设施（浏览器运行器、golden / 截图比对框架、新的 mock 层、生产代码里的仅测试用钩子），
  除非维护者要求。
* 如果测试 diff 超过修复本身的两倍，砍到只剩钉住被报告行为的那几个测试。需要很长准备才能到达的状态，
  通常罕见到不值得修。
* 描述行为所需的测试数量不断增长时，说明实现太复杂了：去简化实现，而不是继续加测试。

## 评审 PR

* 只评审 diff 引入的东西。报告问题前先用 `gh pr diff` 核实归属——如果出问题的行是未改动的上下文，
  那是既有问题，不是这个 PR 的。
* 既有问题单独列在最后一节，不致命的可以不列。绝不把它们混进作者必须修的意见里。
* 重新评审之前，先读作者的回复评论。作者以范围为由拒绝的条目，不要再次提出。
* 准确描述一条意见的后果：区分「值丢了」和「快捷方式失效但值仍然保存了」。
* 修复需要新状态的罕见边角情况，不要报成阻塞项；标为作者可以不修的已知限制。
* 把评审轮次间的增长当作一条意见：如果最新的提交加的状态比原始修复还多，就直接指出，而不是要求更多处理。

## 本地化（`src/lang/*.rs`）

每个文件是一个 `HashMap<key, translation>`。布局如下：

* `template.rs` 是所有键的总表。翻译工作中**绝不修改它**。
* `en.rs` 只放英文显示文本与键本身不同的那些键。
* 其它每个文件（`de.rs`、`fr.rs` 等）都包含完整的键集合；未翻译的条目值为空：`("key", "")`。
* `it.rs` 由其译者手工维护。绝不填写或修改其中的条目；新增键时以 `""` 追加进去，翻译留给维护者。

### 找到一个键的英文原文

填写空条目时，按这条规则确定英文原文：

* 如果 `key` 在 `en.rs` 里存在**且值非空**，那个值就是原文（去 `en.rs` 里查）。
* 否则**键字符串本身就是原文**（键本来就是普通英文）。

然后把原文翻译成该文件的目标语言（从文件里已有的非空条目或文件名推断语言）。

### 翻译规范

* 只填空值。绝不改键，绝不动已有的非空翻译。
* 占位符（`{}`）和转义序列（`\n`、`\"`）与原文保持完全一致。
* 不翻译品牌和技术名词：`RustDesk`、`Socks5`、`TLS`、`UAC`、`Wayland`、`X11`、`TCP`、`UDP`、`2FA`、`RDP`、`D3D` 等。
* URL 类的值（例如 `doc_*` 键）从 `en.rs` 原样复制。

### 新增键（功能开发时）

* 新的英文键用句首大写（sentence case），不用每词首字母大写（Title Case）：写 `Use ID whitelisting`，
  **不写** `Use ID Whitelisting`。缩写（ID、IP、2FA 等）保持大写。遗留的 Title Case 键
  （例如 `Use IP Whitelisting`）保持原样，不要改名。
* 因为键本身就是英文显示文本，句首大写的键通常**不需要** `en.rs` 条目；只有显示文本必须与键不同时
  （例如 `*_tip` 键）才加。
* 每个新键追加到 `template.rs`（值为 `""`）以及每个 `src/lang/*.rs` 文件（已翻译，或拿不准时填 `""`；
  `it.rs` 一律 `""`），都加在列表末尾。
