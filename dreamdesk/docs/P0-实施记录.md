## 设计决定：专业模式怎么判定、怎么谈

> 2026-10-12 用户提问「为什么不去掉模式、把功能点平铺协商」，rustdesk 与 DreamDesk 两个会话讨论后，
> 用户确认。架构文档第 6、7 节由 DreamDesk 会话同步。

**一句话**：两端之间逐项谈能力（平铺）；用户面前只选档位（专业 / 通用），不给一排开关。

| | 决定 | 为什么 |
|---|---|---|
| 1 | **两端逐项交换能力**：能编什么格式、能解什么、显示能不能用，被控端按档位要求挑选 | 失败时能说清缺哪一项；以后某个部件想单独拿出来用，协议不用重做。RustDesk 自己选编码格式也是这个结构（被控端报能编的、主控端报能解的、被控端选） |
| 2 | **用户入口不平铺** | 专业画质链路的各环节互相绑死（丢包恢复靠反馈、编码参数按主控端解码器上限定、全范围颜色要显示端配套还原），拆开单用会坏，而且坏得看不出来——正是「不静默降级」要杜绝的 |
| 3 | **门槛按结果定，不按零件定**；只拿**确定性的格式项**做门槛（实际编出 / 解出的色度、位深），不符立即大声失败 | 零件是实现手段，写进门槛就锁死了实现。格式项从码流里直接读，结果确定、不会抖 |
| 4 | **延迟、丢帧只显示、不卡门槛**：质量面板常驻显示实测值，超标警告，不自动切模式 | 会波动的指标做门槛会让模式来回切换。专业模式目前只用于内网，网络稳定，这样做没有问题（用户确认） |
| 5 | **10bit 条件启用**：被控端桌面是 HDR 才用 10bit，普通桌面用 8bit 加抖动；只在开会话时决定 | 10bit 只有 HDR 桌面才有意义。P0 只做 8bit，10bit 放 P1 |
| 6 | **「模式」是档位 = 一组要求**，不是开关；现在只有「专业」一档，写死一张要求清单，不做通用的档位系统 | 以后「外网专业」、管理员按岗位锁定都是加档位，协议和入口不用改；但现在不为没出现的需求造框架 |
| 7 | **质量面板显示实测值**，不显示对方声称的值；开不起来时写明哪一项不满足 | 界面不说假话 |
| 8 | **只在明确的时间点做决定**（开会话、用户改分辨率、专业通道断开），运行中不因指标波动自己切换 | 稳定、可预期 |
| 9 | **专业通道中途断开**：先自动重连几秒；连不上就退回通用画面，同时挂一个**常驻**的降级提示（不是几秒就消失的弹窗），直到恢复专业模式才撤。P0 恢复方式是重新连接；P1 加「重新进入专业模式」按钮，不做后台自动切回 | 通道断开是确定事件，不是波动指标；提示常驻守住「不静默降级」；不自动切回避免画面来回跳（用户确认，第 4 步实施） |
| 10 | **专业协议版本必须完全一致**，不一致就拒绝并写明双方版本 | 两端统一部署升级；格式错位的最坏结果是「画面花了没人报错」（用户确认） |
| 11 | **P0 阶段两端都开了开关就自动谈判**，不做界面开关 | 模式开关是 P1 的界面工作（用户确认） |

## 插入步骤：产品改名 `dreamdesk-pro`

> 用户 2026-10-13 确认：名称 `dreamdesk-pro`；先做 Windows，Linux 安装包的改名等到第一次要给瘦客户机
> （测试机）出 Linux 安装包时再做（约第 5 步；打包在本机 WSL Ubuntu 24.04 上做，瘦客户机只装包测试）；
> 界面显示名暂时也用 `dreamdesk-pro`，正式显示名到品牌化时再定。

### 为什么

产品后期投入生产，必须用自己的产品名称（用户 2026-10-13 定）。用户提议：**安装包和进程名全部改成
`dreamdesk-pro`**。

### 调研结论（已核对代码）

- RustDesk 内部有一个「应用名」，默认 `RustDesk`。安装目录、安装后的程序名（`应用名.exe`）、Windows
  服务名、配置目录、进程间通信管道名、托盘名都由它派生。所以**只改编出来的文件名不够**：一安装，
  RustDesk 会按应用名在 Program Files 里再生成一个 `RustDesk.exe`，照样被拦。
- RustDesk 官方改应用名的口子（`custom.txt`）要 RustDesk 公司私钥签名，我们用不了；只能自己在程序
  启动最早的时候设置应用名。
- 已有实测佐证「只看文件名」这类外部约束：公司 IT 黑名单按进程名拦 `rustdesk.exe`，同一个程序改名
  `ddtest.exe` 就能运行（见第 2 步「过程中发现的问题」）。这只是测试环境的事实，不是改名的理由。
- 编出来的文件名另有几处写死 `rustdesk`：Flutter 的可执行文件名、Windows 安装包里内嵌的程序名、
  Linux 安装包里的路径和服务文件。
- **`dreamdesk-pro` 和旧版 DreamDesk 不撞**：旧版占用 `C:\Program Files\DreamDesk`、
  `C:\ProgramData\DreamDesk`、服务 `DreamDeskService`、`dreamdesk-server.exe` 等。若用 `DreamDesk`
  做应用名，在测试机上会和旧版的安装目录撞在一起——`dreamdesk-pro` 正好避开。
- 新名字也和官方 RustDesk 不撞：配置目录、管道名、服务名都分开，同一台机器可以并存。

### 方案

1. **新开关 `dd-brand`**，和专业模式的 `dd-pro` 分开：改名对通用模式同样适用，不属于专业模式；
   分开后也能单独验证「改名本身没弄坏 RustDesk」。关掉即上游原名。正式产品两个开关都开。
2. **启动最早处设应用名**：RustDesk 原有文件里加一行钩子（在它读取官方 `custom.txt` 之前），
   把应用名设成 `dreamdesk-pro`。所有进程（界面、`--server`、`--cm`、系统服务）都经过同一入口，
   一处生效全部生效。
3. **编出来的文件名**：在我们自己的打包脚本（`dreamdesk/scripts/`）里处理改名，尽量不改 RustDesk 的
   构建文件；实在绕不开的（比如 Flutter 可执行文件名写死在构建配置里）再改那一行，并写明原因。
4. **两个平台最终都要改。顺序建议先做 Windows**：被控端和现在的开发机都是 Windows，Windows 安装包
   P0 就要用到；Linux 安装包涉及的写死路径多，而 P0 期间瘦客户机上跑的是开发版、还不打 Linux 安装包，
   等到第一次要给瘦客户机（测试机）出 Linux 安装包时一起做（约第 5 步）。打包机是本机的 WSL
   Ubuntu 24.04，瘦客户机只用来装包测试。（用户已确认）
5. **界面上显示的名字暂时也是 `dreamdesk-pro`**：RustDesk 的显示名和文件名是同一个值，拆开要多改
   不少地方；正式的品牌和显示名（如「DreamDesk Pro」）放到后面品牌化时再做。

### 实施细节（动手前补充调研，2026-10-13）

**会出现 `rustdesk` 名字的进程与文件，逐个怎么处理**

| 环节 | 现在叫 | 怎么改 |
|---|---|---|
| 安装后的主程序、Windows 服务、安装目录、配置目录、管道名 | 由应用名派生（`RustDesk`） | 启动最早处设应用名，自动跟着变 |
| Flutter 编出的主程序 | `rustdesk.exe`（写死在 Flutter 构建配置里，开关管不到它） | 打包脚本在编完后改名 `dreamdesk-pro.exe`，不改 RustDesk 的构建配置 |
| 安装包 | `rustdesk-<版本>-install.exe` | 打包脚本输出 `dreamdesk-pro-<版本>-install.exe` |
| 安装包解压后先运行的内嵌程序 | `rustdesk.exe` | 打包时内嵌改过名的 `dreamdesk-pro.exe`；解压目录按它的名字自动变成 `dreamdesk-pro`，打包器不用改 |
| 隐私模式的辅助进程（复制系统的 RuntimeBroker 改名运行） | `RuntimeBroker_rustdesk.exe`（写死，主程序和安装包打包器各有一份） | 两处都加开关：开了叫 `RuntimeBroker_dreamdesk-pro.exe` |
| 加载用的库 `librustdesk.dll` | 不变 | 它不是进程，Flutter 启动程序按这个名字加载，改了反而要动 C++ |

应用名要在两个入口设置：程序总入口（`core_main` 第一行），以及 Flutter 界面初始化（RustDesk 自己的注释说
总入口里的设置在 Flutter 下不一定生效，它在那里又加载了一次定制配置——我们照样在那里也设一次）。

**连带影响：改名后 RustDesk 会把我们当成「定制客户端」**（它判断的依据就是应用名不等于 `RustDesk`）。
这是 RustDesk 给品牌版本设计的正规路径，行为变化如下：

| 变化 | 影响 |
|---|---|
| 不再检查 RustDesk 官方更新、不会自动升级成官方版；设置里「启动时检查更新」隐藏 | **需要的**：否则官方更新会把产品覆盖回原版 RustDesk；我们的升级以后走控制面 |
| 主页 Logo 上方显示「Powered by RustDesk」 | 用户可见；按 AGPL 注明来源也说得过去，品牌化时再定 |
| 多一个「隐藏连接管理窗口」选项 | 无害 |
| 图标改从程序自带资源取 | 无害，品牌化时换图标 |
| 语言、主题默认值的存储方式略不同 | 用户看到的效果一样 |

**暂不改的（显示层面，留给品牌化）**：程序属性里的「产品名称 / 文件说明」（任务管理器「描述」一列会显示
RustDesk）、窗口内部类名、界面文案里的 RustDesk 字样、版本号（安装包文件名暂用 RustDesk 的 1.5.0）。

**打包脚本**：`dreamdesk/scripts/build-windows.ps1`。功能列表由 `build.py --print-features` 给出再加上
我们的开关（不手抄，避免和 RustDesk 的打包逻辑漂移）；编 Rust 库、编 Flutter、改名、打安装包四步。
RustDesk 的 `build.py` 本身不改。

### 验收

- 开关开：编出的程序、安装包、安装后的进程、Windows 服务、配置目录全部叫 `dreamdesk-pro`，**任何环节
  都不出现 `rustdesk` 的名字**；在本机安装并跑一次回环连接（本机恰好有按进程名拦截的 IT 黑名单，
  顺带能证明安装、服务拉起的子进程里没有漏网的 `rustdesk.exe`）。
- 开关关：编出来和上游完全一样（文件名、应用名都是 RustDesk）。
- 与官方 RustDesk、旧版 DreamDesk 在同一台机器上并存不冲突（配置目录、服务名、管道名各自独立）。

### 风险与注意

- 旧版 DreamDesk 的部署脚本会把 `C:\Windows\Temp\dreamdesk-*.exe` 全部拷进旧安装目录：我们的
  测试部署别把 `dreamdesk-pro*.exe` 放在 `C:\Windows\Temp`，否则会被旧脚本误拷。
- RustDesk 会从程序文件名里解析自定义服务器配置（`rustdesk-host=...` 这种写法）；`dreamdesk-pro`
  里的连字符需要实测确认不会被误解析成配置。→ **已实测排除**：安装版被控端连的是默认服务器
  `rs-ny.rustdesk.com`，文件名没被当成配置。

## 插入步骤：产品版不连外网

> 2026-10-13 用户提出「企业内部禁止连接外网」；方案经用户确认（预置内网服务器、关掉会连公网的功能）。

### 现状（已查代码 + 209.32 实测日志）

RustDesk 默认会主动外连，不是我们加的：

| 连到哪里 | 什么时候 | 产品版现状 |
|---|---|---|
| 官方注册服务器 `rs-ny.rustdesk.com` | 被控端常驻进程一直连（登记 ID、探测网络类型） | **正在发生**：209.32 日志里约每 12 秒一次注册、每 20 秒一次探测，都失败（被公司防火墙挡） |
| 四个公网 STUN（Cloudflare、Google 等，写死在代码里） | 按 ID 连接时，IPv6 打洞和 WebRTC 探测公网地址 | 按 ID 连接才触发 |
| 官方账号服务器 `admin.rustdesk.com` | 用户点登录、用地址簿 | 不操作不连；后台心跳对官方地址本来就跳过 |
| 升级检查 `api.rustdesk.com`（带设备指纹） | 启动时 | **不会连**：改名后是「定制客户端」，RustDesk 自动关掉升级检查 |

IP 直连（我们现在的用法）不经过注册服务器和 STUN；专业画面通道只在内网两台机器之间直连。

### 方案

产品版（`dd-brand`）启动时，在改名的同一处把下面几项写进 RustDesk 的**强制设置**（官方定制客户端用的就是这一层；
用户在界面上改不了，不可能误配回公网）：

| 设置 | 值 | 作用 |
|---|---|---|
| 注册服务器 `custom-rendezvous-server` | `dreamdesk.of3d.com` | 不再连官方注册服务器 |
| 中继服务器 `relay-server` | `dreamdesk.of3d.com` | 不再用官方中继 |
| 账号服务器 `api-server` | `https://dreamdesk.of3d.com` | 登录、地址簿只发往内网 |
| IPv6 打洞 `enable-ipv6-punch` | 关 | 它用写死的公网 STUN 探测地址 |
| WebRTC `enable-webrtc` | 关 | 没配内网 STUN 时它补上写死的公网 STUN |
| 「ID / 中继服务器」设置入口 | 显示为禁用（灰色、点不开） | 服务器几项是强制的，界面上改了保存时也会被丢掉，所以入口禁用。起初用 RustDesk 的「隐藏服务器设置」开关整块藏起来，用户要求改为显示但禁用（2026-10-13）：RustDesk 没有现成的禁用开关，在桌面设置页加一处判断——这项被强制设置时入口禁用（判断用 RustDesk 现成的「是否锁定」） |
| WebRTC 的 STUN `ice-servers`（实施时补） | `stun:dreamdesk.of3d.com:3478` | 被控端应答别人发来的 WebRTC 邀请时**不看本机开关**（RustDesk 注释写明是故意的），没配 STUN 就补写死的公网 STUN；配一个内网的就不补 |

- RustDesk 已有的相关逻辑（已查代码）：注册服务器不是官方的，RustDesk 就把 UDP 打洞、IPv6 打洞、WebRTC 的**默认值**
  设成关；但用户在界面上手动打开仍会去连公网 STUN，所以后两项改为强制关。UDP 打洞只经我们自己的注册服务器，不涉及
  外网，照 RustDesk 默认（关）。
- 用强制设置而不是默认值：默认值会被机器上已有的配置盖掉；强制设置统一部署、统一升级，服务器地址变了就发新版。
- 设置都在 `src/ddpro/brand.rs` 的 `apply()` 里加（它已经在每个进程的最开头被调用）。
- **实施时发现、只能改代码的一处**：RustDesk 启动做网络类型探测时**无条件**顺带用写死的公网 STUN 探测公网 IPv6
  地址，不看 IPv6 打洞开关（第一次验收时 209.32 的 DNS 里出现了 `stun.antisip.com`、`stun.cloudflare.com`）；被控端
  收到对方提供的 IPv6 地址时还会按需再探测。在这个探测函数开头加一行：产品版（`dd-brand`）直接不探测——一处管住
  全部调用路径；不开产品开关时走原来的代码。产品版的 IPv6 打洞本来就是强制关的，探测结果没有用处。

## 第 1 步：代码骨架 + `dd-pro` 开关

> 这一步在「先说明再动手」的规矩定下之前已经做完，这里补记，请验收。

### 做了什么

在 RustDesk 仓库里给我们的代码建了家，并加了一个编译开关 `dd-pro`：
- 开关关着（默认）：编出来的程序和官方 RustDesk 完全一样，我们的代码根本不参与编译。
- 开关打开：我们的代码一起编进去。目前只是空壳，还没有任何功能。

### 方案选择

| 选择 | 理由 |
|---|---|
| 只建 P0 要用的 5 个模块：门面（RustDesk 只认它）、媒体通道、编码、解码、显示 | 数位板、麦克风、USB 三个到 P2 用到时再建。空壳提前建出来没有用处，反而要跟着维护 |
| RustDesk 只依赖「门面」一个模块，其它模块由门面带进来 | RustDesk 这边的改动只有一行依赖、一行开关，以后加减模块都不碰 RustDesk 的文件 |
| **不改** RustDesk 工作区的成员清单 | 实测：我们的模块被门面引用以后，会自动算作工作区成员。这样少一处可能和上游冲突的地方。（这条回答了架构文档第 5 节「动手时验证」的那个问题。） |

## 第 2 步：专业协议与谈判

### 目标

普通远程连接建立以后，两端自动走完「名片 → 请求 → 同意 / 拒绝」的谈判。
这一步还不传画面，只把谈判流程和版本比对做通。

**验收**：
- 日志里能看到双方谈通了专业协议；
- 编两份版本号不同的程序互连时，握手被明确拒绝，日志写清双方版本、哪一端旧；
- 开关关着的程序和开着的程序互连：普通远程照常工作，不发起谈判，也不报错。

### 方案

1. **消息怎么走**：放在 RustDesk 原有的加密连接里，开一个「专用信封」。RustDesk 的协议只多一行，
   信封里装什么由我们自己的代码解析，以后我们的消息怎么改都不碰 RustDesk。
   （架构文档第 3 节第 5 条已定。）
2. **消息定义工具**：用和 RustDesk 同一套协议库、同一个版本，不引入第二套。（以 RustDesk 为准。）
3. **版本规则：两端必须完全一致，不一致就拒绝。**
   - 为什么这么严：专业模式的两端是我们统一部署、统一升级的。协议格式一旦错位，最坏的结果是
     「连上了，画面却是花的，也没人报错」。严格相等最简单，也最不会出这种事。
   - 以后要是真需要新旧版本混用，再放宽成「取双方都支持的最高版本」，也就是 RustDesk 这次新加密
     握手用的那种做法。
   - 拒绝时提示里同时写出双方的版本号，一眼就能看出该升级哪一端。
4. **谈判流程**（按上面「设计决定」第 1 条，逐项交换能力）：
   1. **被控端递名片**：登录应答里本来就有一段「平台附加信息」（可随意加字段），在里面只加一项
      「支持专业协议，版本 N」。名片只用来让主控端知道「可以谈」，详细能力不放这里——RustDesk 的
      字段保持最小，能力清单放在我们自己的消息里，跟着我们的协议版本走。
   2. **主控端自查并发请求**：先比版本，不一致就不发，直接报错并写明双方版本；一致就查本机能解什么
      格式、专业显示能不能用，把这份清单连同档位（「专业」）一起发出去。
   3. **被控端拍板**：再核一次版本（防御）；**此刻**检测编码能力（显卡能编什么、编码器有没有空位）——
      放在这时查而不是登录时查，因为编码器占用是实时状态；按固定优先顺序挑双方都支持的第一个格式：
      满足档位要求就回「同意 + 选定格式」，否则回「拒绝 + 缺哪一项」。
   4. 两端都把结果写日志（成功一行、失败一行写明原因），P1 再上界面。
   - **第 2 步只搭这个流程**：版本比对做全；「能编什么 / 能解什么 / 显示能不能用」这几项的检测分别在
     第 3、5 步接入。第 2 步里这几项如实报「未检测」，谈判结果日志写「协议已谈通，能力未检测」，
     不假装支持。
5. **何时发起**：
   - P0 阶段两端都开了专业开关就**自动发起**，不做界面开关。模式开关是 P1 的界面工作。
   - 只在「远程桌面」这类会话里发起。文件传输、终端、端口转发这些会话不发。
   - 每个会话只谈一次（「设计决定」第 8 条）；改分辨率等重启点到第 3 步再接。
6. **安全**：被控端只在**已经登录授权的远程桌面会话**里处理我们的消息。这一点 RustDesk 本身已经
   做了：它按会话类型给消息设了白名单，远程桌面类型放行，其它类型直接拒收（已核对代码）。不需要
   我们另写一套检查。

### 方案落地时的细节决定

- **日志节流**：被控端 / 主控端「收到对端专业协议消息」时写的日志，发送频率由对端决定，按 RustDesk 的

- **纯逻辑和接线分开**：协议编解码、版本比对、格式挑选放在 `dreamdesk/crates/ddpro`（不依赖 RustDesk，
  单独几秒就能编）；和 RustDesk 内部类型打交道的只在 `src/ddpro/`。

### 过程中发现的问题

1. **公司 IT 把进程名 `rustdesk.exe` 列入了软件黑名单**，一运行就被结束并删除文件（用户确认）。
   测试版一律改名 `ddtest.exe`。**最终产品必须改可执行文件名和品牌**，已由 DreamDesk 会话写进架构文档
   第 8 节「迁移时一并满足的需求」第 5 条。
2. **「93 处消息匹配可能编不过」的风险不存在**：协议库生成的消息类型带「必须写兜底分支」的标记，
   RustDesk 现有的每一处匹配早就被编译器逼着写了兜底，加字段不会让任何一处编不过。架构文档第 10 节
   P0 判据里那句理由已删（DreamDesk 会话改）。
   边界（DreamDesk 会话补充核实）：这个标记只约束**定义消息类型的 `base` 之外**的代码；`base` 自己目前
   没有匹配消息类型，所以成立。以后若有人在 `base` 里面匹配它，就没有这层保护——开关开 / 关两种编译
   检查（P0 判据）照样能兜住。
3. **开发环境的坑**：
   - RustDesk 旧界面（Sciter）配最新的 sciter.dll 在新版编译器的调试版下会崩、在关掉调试断言后界面

## 第 3 步：被控端 NVENC 4:4:4 编码

### 目标

被控端把屏幕画面直接在显卡上编成 **HEVC 4:4:4 8bit** 码流，全程不回读到内存。这一步只管「编得出来、
编得对、编得快」，还不发给主控端（发送是第 4 步）。

**验收**（全部机器判据）：
- 在 192.168.209.32（RTX 4060）上采集真实桌面、编码 N 秒，存成码流文件；用 ffprobe 读码流头：
  色度 `yuv444p`、8bit、HEVC Range Extensions（4:4:4 专用的档次），读出来不是 4:4:4 就算失败；
- 码流头里的颜色说明是 BT.709、全范围；
- **编码侧颜色比对**：验证工具在编码的同时抓一帧原始画面留作对照，码流用 ffmpeg 按码流里的颜色说明
  解回 RGB，和原始画面逐像素比：报每个通道的最大误差和平均误差（PSNR）。误差标准先实测出一个基线，
  抖动关时误差应只剩编码损失；这一步先把「编码这一侧颜色是对的」证明掉，端到端的颜色比对等主控端
  做出来再补；
- 码流能被 ffmpeg 正常解码成画面（抽几帧存成图片，人眼看一眼画面是不是桌面——这是唯一需要看的地方）；
- 每帧「拿到画面 → 编码完成」的耗时、帧率、每帧大小，打出统计（平均 / 95 分位 / 最大）；
- 第 2 步谈判里的「编码能力」从「未探测」变成真实探测结果：被控端问显卡驱动能不能编 HEVC 4:4:4 8bit /
  10bit，写进答复；本机 GTX 980 Ti 上应探测为「不支持 4:4:4」并如实报出（不支持就大声说，不悄悄降级）。

### 方案

1. **采集：直接用 RustDesk 的屏幕采集模块**，打开它的「输出显卡纹理」开关，拿到的是显卡上的画面和
   它所在的显卡设备。我们的编码器就用同一个设备，画面不出显卡。
2. **编码器：自己直接调 NVENC**（RustDesk 现有的硬件编码不支持 4:4:4，见架构文档第 2 节）。
   - 接口定义用 NVIDIA 官方头文件（MIT 风格许可，RustDesk 依赖的编码库里就带着），**一次性生成 Rust
     绑定并提交进仓库**，不在每次编译时生成——省得每台编译机都要装 LLVM。
   - 运行时动态加载显卡驱动自带的 NVENC 组件，不需要装 NVIDIA SDK；没有 N 卡的机器上加载失败就报
     「不支持」，不影响程序其它部分。
   - 参数：HEVC 4:4:4、低延迟预设、恒定码率、不用 B 帧、关键帧只在需要时发（开会话、对端要求时）。
     「画面静止后逐步变清晰」需要的那个编码器开关（逐块调质量）**创建时就打开**，因为运行中打不开——
     P1 做静止收敛时直接用，不用重建编码器。码率 P0 先固定一个值（默认 30 Mbps，内网够用），可调。
3. **颜色转换：自己在显卡上做，一开始就做准**（用户 2026-10-13：不赶进度，不走临时方案）。
   - 不交给 NVENC 内部转换：那样色彩矩阵、全 / 有限范围由驱动决定、我们控制不了，也说不清它对不对。
   - 着色器把 RGB 画面转成 4:4:4 的 YUV：**BT.709 色彩矩阵、全范围**（8bit 的 0–255 全用上，不压到
     16–235），并把这两项写进码流的颜色说明里，让任何标准解码器都按同样的规则还原。
   - 8bit 转换有舍入误差，大片渐变会出色带；转换时加**有序抖动**（固定图案，静止画面逐帧完全一致，
     不会因为抖动让「画面没变」判断失效）。抖动做成开关，留给 P1 的「精确模式（关抖动）」。
   - NVENC 吃哪种 4:4:4 内存排布（打包的 AYUV，还是 Y/U/V 三个平面）由显卡驱动的实际支持决定，
     动手第一件事在 4060 上实测确认；不论哪种，都由下面的「编码侧颜色比对」兜底验证。
   - 着色器源码放 `crates/ddpro-enc/shaders/`，编译时用 Windows SDK 自带的编译器编好嵌进程序
     （编译机本来就要装 VS，不新增依赖）。
4. **线程**：采集和编码在**同一个线程**、用同一个显卡设备。NVENC 和采集共用设备时跨线程调用容易在
   驱动里互锁，干脆从结构上排除。
5. **这一步不接入 RustDesk 的会话**：做成 `dreamdesk/crates/ddpro-enc` 里的一个独立验证工具
   （采集 + 编码 + 存文件 + 统计），先把编码这一环单独验证干净；接进 RustDesk 的服务、跟着专业会话启停，
   在第 4 步和传输通道一起做。唯一接进 RustDesk 的是第 2 步谈判里的「编码能力探测」。
6. **在 209.32 上怎么跑**：屏幕采集只能在有人登录的桌面会话里做，远程管理通道那种后台会话采集不到。
   209.32 上登录着你的账号（控制台会话）；用一次性计划任务把验证工具放进这个会话里跑，跑完删任务。
   不需要你登录或操作。那台上同时跑着旧版 DreamDesk、UU 远程、ToDesk——它们也在采集 / 编码，验证工具
   和它们并存；N 卡同时能开的编码会话有上限，若被占满会如实报错。

### 这一步对 RustDesk 的改动

几乎没有：编码能力探测接在第 2 步已有的接入层里（我们自己的文件）；验证工具在我们自己的目录。
RustDesk 原有文件不动。

### 已知的后续风险（不影响 P0）

- **HDR 桌面**：RustDesk 采集模块拿到 HDR 画面时会先压成 8bit 普通画面再交出来。P1 做 10bit 要拿到原始
  HDR 画面，可能要在 RustDesk 的采集模块里加一个开关（改上游代码），到时单独出方案。
- **同一块屏同时被通用模式和专业模式采集**（架构文档待决问题第 5 条）：这一步的验证工具和旧版 DreamDesk
  并存时会顺带看到两路采集能不能共存，结果记下来。

### 决定记录

- 颜色转换自己做、一开始就做准（用户：不赶时间和进度）。技术细节由我定，理由写在上面。
- 在 209.32 上用户登录着的桌面会话里跑验证工具（计划任务，跑完即删）：测试机，我定。
- 验证用的 ffmpeg / ffprobe 下载官方静态版放 `D:\WORKPLACE\CODING\_toolchain\ffmpeg\`，只在开发机上用，
  不进产品。

### 实施中的发现与决定

- **NVENC 在 D3D11 下不接受「Y/U/V 三平面叠在一张纹理里」的排布**（注册输入报参数不支持，错误码 12）→
  改用打包的 **AYUV**（着色器通过 RGBA 视图直接写 AYUV 纹理），一次通过。三平面那条路删掉，不留后备。
- **采集输出显卡纹理绑在 RustDesk 的 `vram` 功能上**（采集模块的通用接口和底层接口都是）。查 CI：
  **官方 Windows x64 发布版本来就用 `--hwcodec --vram` 构建**，而我们之前的打包只用了 `--flutter`，
  和官方不一致。→ Windows 打包脚本默认改为 `--hwcodec --vram`（与官方对齐，通用模式和原版一样），
  验证工具也用 `vram`。第 4 步把专业视频服务接进 RustDesk 时，产品构建本来就带 `vram`。
- 着色器编译用 Windows SDK 的 `fxc`，编译时嵌进程序；NVENC 接口用官方头文件（MIT 风格许可，放在
  `crates/ddpro-enc/nvenc/`）一次性生成的 Rust 绑定（`src/nvenc_sys.rs`，提交进仓库，编译机不需要 LLVM）。
- 在测试机上跑：一次性计划任务以控制台登录用户的身份、交互式登录类型运行（落在他的桌面会话里），
  `conhost --headless` 不弹控制台窗口（第一轮弹出的黑窗被采进了画面），跑完即删任务。

## 第 4 步：专业画面通道 + 接进 RustDesk 会话

### 目标

专业会话谈成后，被控端把第 3 步编出的 4:4:4 码流，通过一条**独立、加密的 UDP 通道（内网直连）**实时送到
主控端；同一时间这个连接的普通画面停掉，键鼠、声音、剪贴板等照旧走 RustDesk 原通道。主控端这一步只负责
**收齐、检查、存文件**，解码和显示是第 5 步。

### 验收（全部机器判据）

- **被控端 209.32**（装带专业模式的测试版）↔ **主控端用本机开发机**（只收不解码，不需要 4:4:4 显卡；
  不打扰瘦客户机）：
  - 谈判同意后通道自动打通；主控端收到的码流存成文件，ffprobe 确认是 4:4:4；
  - **传输无损**：被控端同时把它发出去的码流存一份，两份逐字节相同（不丢包时）；
  - 收发统计：帧数、包数、丢包数、吞吐、帧到达间隔的抖动；
- **丢包恢复**：用诊断开关让接收端按比例故意丢包 → 主控端发现断档 → 通过 RustDesk 原连接请求关键帧 →
  被控端补发 → 码流恢复可解；记录每次「发现断档 → 收到关键帧」的耗时；
- **回退**：断掉专业通道（关掉接收端）→ 被控端几秒内发现、退回普通画面，普通远程继续可用，日志写明原因；
- **普通远程不受影响**：同一会话里键鼠、剪贴板照常，开关关着的版本互连照常（第 2 步那几轮重跑一遍）。

### 方案

1. **谈判补上通道信息**：被控端「同意」时附带：自己的 UDP 地址（RustDesk 连接是从被控端哪个地址进来的，
   主控端就能连到那个地址；端口是新开的）、一次性令牌、加密密钥。这些都经 RustDesk 已加密的连接传，
   不落在明文里。消息内容变了，**专业协议版本升到 2**（规矩：两端版本必须一致）。
2. **谁先发**：主控端先往被控端地址发「打招呼」包（带令牌），被控端只认第一个带对令牌的来源地址，之后把
   画面发到那里。这样定的依据（已查代码）：RustDesk 安装时防火墙按**程序**放行入站和出站，被控端收得到；
   主控端主动往外发，它那边的防火墙也不用开口子。3 秒打不通 → 判定专业通道失败，按第 9 条决定退回普通画面。
3. **打包格式用标准 RTP（H.265 的标准打包方式）**，每包不超过 1200 字节（内网不分片）；
   **加密用标准 SRTP（AES-128-GCM，带完整性校验，被篡改的包直接丢弃）**。两者都复用 RustDesk 已经依赖的
   WebRTC 组件里的现成实现（`rtp`、`webrtc-srtp`），**不新增依赖、不自己写加密**。
4. **丢包怎么办（P0 最小做法）**：不重传、先不做纠错码（纠错码在 P1）。主控端按包序号发现断档 → 丢掉不完整
   的帧 → 经 RustDesk 原连接发「请求关键帧」→ 被控端下一帧编成关键帧。关键帧本来就只在需要时发（第 3 步），
   这条反馈是必需的，不然一丢包画面就一直坏着。
5. **被控端专业视频服务，复用 RustDesk 的服务框架**：每块屏一个专业服务，和普通画面服务同一个模式——要用时
   按屏注册，谈成后这个连接**退订**这块屏的普通画面、**订阅**专业服务；服务在第一个订阅者到来时启动、最后
   一个离开时停止；**连接断开时 RustDesk 在锁内统一退订，专业服务随之停止，没有竞态**。服务循环在一个线程里：
   RustDesk 采集器取画面 → 第 3 步的编码器 → 打包加密 → 发送。专业通道本身失败（心跳超时：网络断、被拦）→
   退订专业服务、重新订阅普通画面。
   - **方案讨论记录（2026-10-13）**：服务框架的模块和「注册服务」的方法在 RustDesk 里只对 `server` 模块内部
     可见。曾考虑为守「只加不改」绕开它，改成「每会话一个线程 + 心跳超时判断会话结束」——那样会话结束后要
     白跑 3 秒、有残留一路普通采集的竞态，还多一套平行的启停机制。用户指示原则可调整、以最优最稳最易维护
     最兼容为准，比较后选用框架：代价是把这两处的可见性从「仅 `server` 模块」放宽到「本程序内」（不改任何
     行为），换来生命周期由 RustDesk 统一管理。
   - **同一块屏：普通模式可以共享，专业模式不能共享**（用户 2026-10-13 选方案 A）：一块屏同一时间只给
     一个专业会话；**开启时这块屏上已经有别人在用普通模式看，也拒绝**，并写明原因（不改 RustDesk 原有的

### 实施中的发现与决定

- **H.265 切包 / 组装自己写（RFC 7798），RTP 包头和 SRTP 复用库里的**：rtp 库自带的 HevcPayloader 遇到不认识
  的 NAL 类型会悄悄丢掉，3 / 4 字节起始码混用时也会切错，和「不静默降级」「传输无损」冲突。
- **同一个进程里同一块屏同时只能有一路 DXGI 屏幕复制**：切到专业画面时，这个连接的普通画面服务要到它下一轮
  循环才放开这块屏，专业服务紧接着建的采集器取不到画面（scrap 报 AddrNotAvailable）。→ 启动阶段「建采集器 +
  取第一帧」整体重试最多 3 秒（实测多花约 0.3 秒），和 RustDesk 普通画面服务遇到采集错误时重建采集器一致。
- **直连端口是 IPv6 双栈，IPv4 主控端连进来时被控端这一侧的地址是 `::ffff:a.b.c.d`**，拿它开 UDP 端口 Windows
  报 10049 → 先还原成 IPv4。
- **Windows 上对端端口关了会招来「端口不可达」，变成下一次接收的 10054**；这类回执也可能凭空出现，不当致命
  错误，通道断没断只看 3 秒内有没有收到包。
- **丢包事件去重**：一次丢包会让同一关键帧后续的几十个分片都残缺，起初每片报一次（1% 丢包时 1544 次、多发 106 个
  关键帧）；改成等关键帧期间残缺分片只计数，新间隙限频 100 ms 再报，等不到 200 ms 再要。顺带修了「刚连上就
  错过第一个关键帧会一直不请求」的潜在卡死。
- **编码能力探测改用这块屏的采集器所在的显卡**，删掉第 3 步自己找显卡的那段（注释里写过的待办）。
- **验证工具的依赖单独一个开关 `harness`**：它打开了 scrap 的 vram，若被工作区整体编译（`cargo test` /
  `check --all-targets`）带进来，会和 RustDesk 主程序没开 vram 时的代码对不上而编不过。
- 209.32 的防火墙三个配置文件都是关的，所以「按程序放行入站」这条路这次没测到；产品安装时 RustDesk 会自动加
  按程序放行的规则（已查代码），防火墙开着的机器上第 5 步部署时再验。

## 第 5a 步：端到端分段延迟测量（第 5 步前置）

> 方案 2026-10-13 写成，用户确认。

### 目标

从「被控端拿到这一帧画面」到「主控端屏幕开始显示这一帧」，拆成 8 段逐段量，每段给中位数 / 95 分位 / 最大值；
8 段之和再和「直接算出的总延迟」对账。架构文档要求「可测量性第一天就带上」，「新的不差于旧的」要靠它判，
所以放在解码显示之前：5a 先做前 4 段（被控端 + 网络），第 5 步加解码、显示那 4 段时直接接上。

### 旧实现审查（当参考，不照搬）

旧 DreamDesk 有「六段账本」（`client/src/dd_latency_ledger.h`、`common/src/dd_latency_sei.h`）。看下来：

- **可取**：被控端的分项随帧带过来、用本机差值，不需要对时钟；解码那段的终点放在「GPU 真正画完」之后
  （它踩过：终点放早了，3.3 ms 记到了下一段）。这两条保留。
- **有问题**：
  - 网络那段是**拿 TCP 控制连接往返时间的一半估的**，不是视频走的 UDP 路径，旧代码注释自己也承认「近似得不小」；
  - 总延迟因为一个取数函数被两处调用、先到的把数据取走了，**上线后一次都没算出来过**（恒为 `--`）；
  - 分段之和和总数从不对账，错了看不出来。
- 旧实现不经合成器（自己接管屏幕输出），所以没有「交给合成器 → 上屏」这一段；我们改成窗口交给合成器，
  这一段恰恰最需要量（第 6 步 GNOME 验证就靠它）。

### 8 段怎么切（首尾相接，没有缝也没有重叠）

| # | 段 | 起点 → 终点 | 在哪量 | 哪一步做 |
|---|---|---|---|---|
| 1 | 编码 | 拿到画面 → 编码完成（含颜色转换） | 被控端 | 5a |
| 2 | 发出 | 编码完成 → 第一个包发出 | 被控端 | 5a |
| 3 | 网络 | 第一个包发出 → 第一个包到达 | 跨两台机器（要对时） | 5a |
| 4 | 到齐 | 第一个包到达 → 最后一个包到达（含发送端连发耗时 + 网络抖动） | 主控端 | 5a |
| 5 | 解码 | 最后一个包到达 → 解码完成（等 GPU 画完） | 主控端 | 5 |
| 6 | 转换 | 解码完成 → 颜色转换 + 缩放完成 | 主控端 | 5 |
| 7 | 提交 | 转换完成 → 交给合成器 | 主控端 | 5 |
| 8 | 上屏 | 交给合成器 → 合成器报告这一帧开始显示 | 主控端 | 5 |

量不到的两截，写明、不报假数：被控端桌面画好 → 采集拿到（在 Windows 屏幕复制内部，最多一帧间隔）；
显示器面板自己的延迟（要外部设备拍屏）。

### 两台机器的时钟怎么对

只有第 3 段跨机器。用网络授时的标准算法（NTP 那一套）：

- 主控端本来每 0.5 秒发一次心跳，心跳里带上自己的发送时刻；被控端收到后回一个包，带上「收到时刻、回包时刻」；
  主控端收到时用这四个时间算出**往返时间**和**两边时钟差**。
- 取最近几秒里往返时间最小的那次的时钟差（排队干扰最小），并且持续更新——两台机器的时钟会慢慢走偏，
  每分钟可能差几毫秒，只对一次不行。
- 误差上限是往返时间的一半；内网往返零点几毫秒，所以误差在零点几毫秒以内，比要量的数小一个量级。
- 往返时间是在**视频走的同一条 UDP 路径**上量的，顺带修掉旧实现「拿 TCP 估 UDP」的问题。
- 自检：本机自测（两端同一台机器、同一个时钟）算出的时钟差必须接近 0，不然算法有错。

### 每帧的时间怎么带过去

被控端在每帧**第一个包**的 RTP 包头扩展里带上：拿到画面的时刻、编码完成的时刻、首包发出的时刻（被控端时钟）。

- 为什么用包头扩展、不用旧实现的「塞进码流」（SEI）：包头扩展是 RTP 放传输附带信息的标准位置（WebRTC
  带采集时间也是这么做）；不改码流，第 4 步「两端码流逐字节相同」的验证照样能做，解码器也完全看不到它；
  SRTP 照样校验包头，被篡改的包直接丢弃。
- 消息格式变了（包头扩展 + 授时回包），**专业协议版本升到 3**。

### 输出

- 主控端日志每 5 秒一行：每段的中位数 / 95 分位 / 最大值、总延迟、往返时间、时钟差（定时汇总，不是每帧一行）。
- 诊断开关 `DDPRO_DIAG_LATENCY=文件`：每帧一行 CSV（各段微秒数），事后分析用。
- 界面上的质量面板是 P1（设计决定 7），P0 只出日志和 CSV。

### 验收（全部机器判据）

- **本机自测**（`loopback` 示例，同一时钟）：时钟差 ≤ 0.1 ms；前 4 段齐全；分段之和与直接算的总数相差 ≤ 0.1 ms。
- **真实会话 209.32 ↔ 本机**（只收不解的诊断模式，和第 4 步一样，不碰瘦客户机）：前 4 段都有数；往返时间、
  时钟差稳定；连跑 10 分钟，时钟漂移被持续跟上（第 3 段不随时间单调漂走）。
- 普通远程不受影响；开关关着的版本互连照常。

| 网络（首包发出 → 首包到达） | 0.22–0.28 | 0.32–0.42 |
| 到齐（首包到达 → 末包到达） | 0.03 | 0.08–0.14 |
| **合计（拿到画面 → 末包到达）** | **6.2–7.8** | **8.7–11.1** |

往返 0.19–0.24 ms；两台机器的时钟差 20 秒内从 1.38 走到 1.60 ms（相对走偏约 11 ppm），授时持续跟上，网络一段无负数。
**被控端编码一段占九成以上**，以后优化延迟首先看它（第 3 步的验证工具量到的编码耗时也是约 6 ms）。

**10 分钟连续运行**（同样条件）：21301 帧新画面，网络一段 p50 0.25 / p99 0.59 / p99.9 0.99 ms，无负数；两台机器的
时钟差 10 分钟内从 0.89 走到 7.12 ms（约 10 ppm），授时全程跟上（网络一段不随时间漂）；会话结束时专业服务正常收尾。
偶发尖峰：13 帧的网络一段超过 2 ms，形态都是「停顿一次、后几帧排队补上」（如 87 → 71 → 38 → 4 ms），10 分钟里两三次；
现有数据分不清是主控端线程短暂没被调度还是虚拟机网络偶发延迟，不影响结论。

**第一次 10 分钟运行在第 9 分半回退到了普通画面**（未复现，记录在案）：主控端收画面的线程卡住约 20 秒——网络一段
最大值先涨到 41、75、928 ms（包已到、线程没读），随后每 5 秒的汇总断了 24 秒；心跳由同一线程发，被控端 3 秒收不到
心跳，按设计退回普通画面（这一步行为正确）。当时本机正同时跑 Windows 和 WSL 的整套编译检查（CPU 占满），时间重叠；
本机不做别的事重跑同样 10 分钟没有出现。最可能是测试期间本机的编译负载，未完全证实。
**由此给第 5 步定一条约束**：收包、发心跳的线程必须和解码、显示分开，解码偶尔慢一下不能被当成通道断开。

### 实施中的发现与决定

- **被控端用单独的小线程收心跳、立即回授时包**。原来心跳由发画面的循环每帧顺手读一次，读到时包可能已在缓冲里
  躺了大半帧（最多约 16 ms），「收到时刻」不准，授时会被拖偏几毫秒。线程随发送端一起结束。
- **心跳（兼授时探测）从每 0.5 秒改为每 0.1 秒**，对时只取最近 2 秒里往返最快的那次：两台机器时钟相对走偏实测
  约 11 ppm，窗口太长会用到过时的时钟差。
- **至少 5 次授时才开始用对时结果**：第一轮实测通道刚打开的头 0.1 秒只有一两个样本，挑到的那次往返偏大，时钟差偏了
  1.5 ms，网络一段成了负数；之后稳定。凑够 5 次（0.5 秒）之前的帧照收，只是不记网络一段。
- **被控端回授时包用单独的 SSRC**：两个方向共用一把密钥，SRTP 的加密初始向量由 SSRC 和序号决定，每条发送流必须有
  自己的 SSRC，否则初始向量重复，AES-GCM 的保密和防篡改都会失效。
- **只给新采集到的画面带时间**：第一帧在通道建立前就取了（含等主控端打招呼的时间），没有新画面时编码器重复上一帧，
  这两种都不带——它们的「延迟」没有意义，带上只会污染统计。
- **负值照记不丢**：网络一段出现负数说明对时有误差，要让它露出来（旧实现是丢弃负值）。
- 包头扩展只加在每帧首包上，首包的第一个 NAL 按扩展的 24 字节少切一点，其余包不变，不浪费带宽。
- **开发版（不优化）程序库测出的「到齐」约 4 ms，优化编译后 0.03 ms**：差别在加密打包的速度。测延迟必须用优化编译，
  开发版只能验功能。
- 测试画面脚本（PowerShell）必须是纯 ASCII：Windows PowerShell 5.1 按本地编码读无 BOM 的文件，中文注释乱码后把
  下一行的参数声明「吞」了。

## 第 5 步：主控端硬解 + `--pro-view` 原生窗口

> 方案 2026-10-13 写成，用户确认。

### 目标

瘦客户机（Linux）上：专业码流用显卡硬解、保住 4:4:4，颜色按 BT.709 全范围准确还原，**全程不经 CPU 拷贝**交给
系统显示；键鼠在这个窗口里操作远程桌面；5a 的后 4 段延迟接上。
**P0 范围**：一块远程屏、全屏显示、8bit、Wayland 桌面；系统快捷键拦截、数位板不做（用户 2026-10-13 接受，放 P1）。

### 一句话做法

新开一个独立进程 `--pro-view`：自己收专业码流 → 显卡解码 → 显卡把 YUV 4:4:4 转成 RGB（顺带缩放到屏幕大小）→
把显存里的画面直接交给系统合成器显示；键鼠转给 RustDesk 会话发出去。RustDesk 原来的 Flutter 窗口保留，
当控制面板（工具栏、Ctrl+Alt+Del、断开等）。

### 各部分怎么选

**1. 独立进程 `--pro-view`，不放进 Flutter 进程**

- RustDesk 自己有一模一样的先例：白板功能就是一个独立进程角色（`--whiteboard`），用 winit 开原生窗口，
  经 RustDesk 的进程间通道收数据（已查代码）。照这个先例做，不另立一套机制。架构文档本来就这么定，不用改。
- 显卡驱动（解码、颜色转换）出问题时只崩这个窗口，不连累 Flutter 界面和其它会话——旧实现记录过 N150 上
  4:4:4 硬解偶发报错。
- 代价：键鼠、光标要经本机进程间通道转一手（几十微秒，相对一帧 16 ms 可忽略）。
- 另一种是在 Flutter 进程里开线程画窗口，省掉进程间通道，但驱动出错会带走整个界面。不选。

**2. 解码：用 RustDesk 已经带着的 FFmpeg 7.1.1 + VAAPI 硬解，不加依赖**

- 已查：RustDesk 的 Linux 版 FFmpeg 本来就编进了 HEVC 解码器和 VAAPI 硬件加速；官方 Linux 发布版带 `--hwcodec`，
  安装包本来就依赖 libva。专业版 Linux 构建同样带 `--hwcodec`（和 Windows 对齐官方的做法一致）。
- FFmpeg 7.1 的 VAAPI 解码按源码应支持 HEVC 4:4:4，**第一件事就在瘦客户机上实测确认**。
- 没选的：直接调 libva 要自己解析 H.265 切片头，量大易错；GStreamer 是新的大依赖；纯 Rust 的 VA-API 解码库
  对 4:4:4 的支持不确定。
- **格式门槛**（设计决定 3）：第一帧解出来检查实际格式，必须是 4:4:4 8bit，不是就大声失败、退回普通画面并写明原因。
- 出错处理先做最简单的：单帧报错 → 请求关键帧、继续显示上一帧；连续报错 → 重建解码器。旧实现那套复杂的恢复
  策略不照搬——先实测现在的驱动（iHD 25.2.4）还会不会出旧记录里的报错。

**3. 颜色转换放在显卡的视频处理单元，转成 RGB 再交给合成器**（和旧实现最大的不同，请重点看）

- 旧实现把 YUV 画面直接挂到显示硬件上，颜色范围靠设置显示硬件的属性「钉死」。换成窗口交给合成器后，
  **我们没有权限碰显示硬件**；而把 YUV 交给合成器时，「请按 BT.709 全范围还原」这句话目前没有协议能告诉它
  （Wayland 管这事的新协议，GNOME 46 还不支持）——颜色对不对就不在我们手里了。
- 所以由我们自己在显卡上把 YUV 4:4:4 按 **BT.709 全范围**明确转成 RGB，合成器拿到普通 RGB 画面，任何合成器
  都不会理解错。转换用显卡的**视频处理单元**（专门的固定功能电路，VAAPI 的视频后处理接口），不占 3D 渲染单元；
  同一步顺带缩放（远程分辨率和本地屏幕不一样时）。
- 4:4:4 转 RGB 不损失色度：每个像素本来就有完整颜色，转换只是换一种表示。
- 合成器拿到全屏 RGB 画面，通常可以直接送显示硬件、不再合成一遍——做不做得到要实测，第 8 段会直接显示出来。
- **风险**：视频处理单元的转换精度、范围设置驱动实现得对不对，要用颜色准确性判据验（见验收）。万一不对，退路是
  用 3D 单元跑我们自己写的着色器（和被控端编码前那步一样，公式完全在我们手里），代价是占 3D 单元。
- 还剩一级管不到：显卡输出到显示器那一段（HDMI 可能按电视的 16–235 范围输出，画面发灰），由合成器设置，
  第 6 步查瘦客户机的实际值。

**4. 窗口：winit + Wayland 的零拷贝画面协议**

- winit（开窗口、全屏、键鼠、光标）和 Wayland 客户端库，RustDesk 都已经依赖（白板、剪贴板在用），不加新依赖。
- 画面经 Wayland 的 dmabuf 协议交给合成器（零拷贝）；用「呈现反馈」协议拿每帧实际开始显示的时刻（第 8 段）。
  GNOME 46 对这两个协议的支持实测时确认。
- **P0 只支持 Wayland 桌面**（用户 2026-10-13 接受）。X11 也有标准的零拷贝显示方式（DRI3 + Present，Linux 显卡驱动
  在 X11 下本来就这么用），不是做不到，而是要多写、多测一套显示代码；而我们的目标环境都是 Wayland（Ubuntu 24.04
  的 GNOME 默认、以后 kiosk 的单程序合成器），GNOME / Ubuntu 新版也在去掉 X11 桌面。X11 下主控端报「显示能力
  不满足」，谈判时就不开专业模式并写明原因（不静默降级）。以后要支持只需加一套 X11 显示代码，解码、转换、通道都不动。
- 永远显示最新一帧：新帧到了立刻提交，不排队，不攒延迟。
- **收包、发心跳的线程和解码、显示分开**（第 5a 步长时间运行得出的约束）：心跳停 3 秒被控端就退回普通画面，解码或显示偶尔慢一下不能被误判成通道断开。

**5. 键鼠和光标**

- 键盘：窗口拿到的原始键码，换成 Flutter 窗口交给 RustDesk 的同一种键码，调用**同一个入口**——RustDesk 的
  键盘映射模式、锁定键处理全部照用，不另写映射。
- 鼠标：窗口坐标换算成远程屏坐标，调用 RustDesk 现有的鼠标入口。
- 光标：会话收到的远程光标图案和位置转给窗口，设成**本窗口的系统指针**（架构文档第 8 节定的做法，和 Flutter
  界面一样由系统画）。
- P0 不做：系统快捷键拦截（如 Super 键先被 GNOME 吃掉）、数位板。

**6. 两个窗口怎么配合（P0 最小形态，用户 2026-10-13 接受）**

- 谈成专业模式 → 会话进程拉起 `--pro-view`，全屏显示。通道参数（地址、令牌、密钥）经本机进程间通道交给它，
  **不放命令行**（命令行别人用 `ps` 看得到）。
- Flutter 窗口保留，停在最后一帧普通画面上，工具栏照常可用。
- 关闭会话 → `--pro-view` 跟着退出；关闭专业窗口 → 被控端退回普通画面，Flutter 窗口恢复普通画面（复用第 4 步的
  回退路径）。
- 专业窗口里的工具栏、模式切换、常驻降级提示是 P1 的界面工作。
- **为什么专业画面不放进 RustDesk 原窗口**（用户 2026-10-13 问）：原窗口里的一切（含远程画面）都由 Flutter 每帧
  重画进它自己的 8bit 画布，再交给系统合成器。即使把 RustDesk Linux 版现在的「拷回 CPU」改成直接交显卡画面，
  仍会每帧多一遍全屏绘制、最多多约一帧等待、10bit 进不去；还要改 RustDesk 的 Linux 界面底层。不经 Flutter 的
  独立显示区域：绘制最少、延迟最低、10bit 可行，代码自成一体在我们目录里。代价是界面和画面不在同一套代码里画，
  「看起来一个窗口」（工具栏画进专业窗口，或用 Wayland 子表面把画面嵌进原窗口）P1 实测对比后再选。

**7. 请求关键帧改走专业通道自己的回程**（调整第 4 步的做法）

- 第 4 步是经 RustDesk 原连接请求关键帧。现在收码流的是 `--pro-view` 进程，再绕回会话进程转发就多一跳。
  改成主控端直接在专业通道上回发——RTP 的标准做法本来就是这样（RTCP 的「请求关键帧」），通道变得自给自足，
  还少了 TCP 排队。丢了照样按 200 ms 重发。
- 协议版本再升一级（v4）。

### 实施顺序（每步都有可跑的验证）

1. **WSL 里编出 Linux 专业版**（Flutter + `dd-pro` + `--hwcodec`）。Linux 的 Flutter 构建在 WSL 里还没跑通过，是第一项准备。
2. **解码 + 颜色转换 + 读回的命令行验证工具**：输入第 3 步在 209.32 上录的码流，在瘦客户机命令行下跑——查实际格式、
   颜色误差、每帧耗时。不需要桌面，显卡解码单元可以和旧客户端共用，只占几十秒显卡（跑前打招呼）。
3. **窗口 + 零拷贝提交 + 呈现反馈**（要 Wayland 桌面，见下面测试环境）。
4. **接进会话**：拉起、传参数、键鼠、光标、关键帧回程、关闭。
5. **联调验收**。

### 验收

- **颜色准确**（机器判据）：用第 3 步验证工具录的码流和原图，主控端把转换后的 RGB 画面读回、和原图逐像素比，
  判据沿用第 3 步（平均误差、PSNR）。这是唯一能抓住「颜色看着对、其实偏了」的办法。另按架构文档补一张标准测试图
  （色块、渐变、细彩线、文字）：细彩线在 4:2:0 下会糊，读回比对能区分 4:4:4 是否真的生效。
- **零 CPU 拷贝**（机器判据）：主控端进程 CPU 占用 + 显卡各单元占用（`intel_gpu_top`）；1440p60 下和 Flutter 普通画面对比。
- **延迟**（机器判据）：8 段齐全，和总数对账；同一台被控端走普通模式做对照。
- **回退 / 关闭**（机器判据）：关专业窗口 → 普通画面恢复；关会话 → 专业窗口退出；X11 下谈判拒绝并写明原因。
- **30 分钟连续运行**不涨内存、不掉帧（长时间稳定性的完整验证在第 6 步）。
- **键鼠**（要人眼）：常用键、组合键、锁定键、鼠标位置在远程正确。

- 视频处理单元颜色转换不准 → 退路是自写着色器（见第 3 点）。
- GNOME 46 怎么处理零拷贝画面（直接送显示硬件还是再合成一遍、长时间跑合成器 CPU 会不会累积）——这就是第 6 步的
  两项验证，第 5 步先拿到数。
- 两个窗口的体验（切换、焦点）P0 只求能用，P1 再打磨。

### 旧实现审查要点（都当待验证的说法，不当结论）

| 旧实现的说法 | 我们怎么看 |
|---|---|
| N150 + mutter 持续导入 dmabuf，合成器 CPU 累积拖垮解码 | 当时的 mutter 版本、导入的是 YUV；我们交的是 RGB，走合成器的另一条路径。第 6 步用现在的 GNOME 46 实测 |
| iHD 硬解 4:4:4 在画面剧烈运动时偶发报错 | 驱动版本已不同（现在 25.2.4）；实测还在不在，出错处理先做简单的 |
| 直出时不等垂直同步翻页省约 8 ms（代价是撕裂） | 合成器下能不能这样取决于合成器；用第 8 段实测，不预设 |
| 解码表面池 12 个够用 | 按我们自己的流程算、实测，不抄数字 |
| GL 合成链占 3D 单元 47.9% | 我们的颜色转换放视频处理单元，不走 3D 单元；`intel_gpu_top` 实测 |
| HDMI 默认按 16–235 输出、画面发灰 | 合成器下我们管不到这一级；第 6 步查实际值，必要时走合成器的设置 |
